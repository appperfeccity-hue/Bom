# Project finalization flow via Supabase RPC

This change adds a complete finalization workflow for consultants: a state machine store that calls `finalize_project` via Supabase RPC, a three-stage UI (button, confirmation dialog, success panel), and toolbar lock controls that disable editing when the project reaches FINALIZED status. Two new enum values (VALIDATED, FINALIZED) extend `ProjectStatus` to gate the flow. The approach mirrors the existing publish workflow pattern (step enum, Zustand store, modal overlays) adapted for a simpler one-shot irreversible action.

Watch for: The client-side hash includes a `new Date().toISOString()` timestamp generated *before* the RPC call, meaning the stored `finalBomHash` and `finalizedAt` are client-determined values that may diverge from whatever the server records (confirmed). The toolbar lock only disables DESIGNER-mode zone buttons, leaving CONSULTANT-mode interactions unguarded if other editable surfaces exist (likely). No concurrent finalization guard prevents double-clicks while the async call is in-flight since the button remains mounted during FINALIZING state (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The hash is computed client-side as SHA-256 of `projectId + finalizationKey + timestamp` then sent to the server RPC — the server is the source of truth for immutability, but the client retains its own copy of the hash and timestamp for display, creating a potential discrepancy if the server computes or stores a different value.

Toolbar integration disables the create-zone and delete-zone buttons when `isFinalized` is true. The lock applies only to DESIGNER-mode zone controls; any CONSULTANT-mode editing affordances (current or future) are not gated.

The test suite does not exercise the race condition between two rapid confirmations, nor does it verify that the lock propagates to non-toolbar editing surfaces.

<details>
<summary>Issues (4)</summary>

1. **Client-side timestamp divergence** — `finalizedAt` and `finalBomHash` are derived from a client `new Date()` before the RPC returns. If the server's `finalize_project` function records its own `now()`, the displayed timestamp won't match the database. Use the server response to populate these fields, or accept the discrepancy as intentional and document it.
2. **Double-submit during FINALIZING** — The Confirm button in the dialog is only disabled by `isLoading`. If `isLoading` hasn't flushed to a re-render before a second click fires, `confirmFinalization` can be called twice with different keys/hashes. Add an early return or guard in `confirmFinalization` when step is already FINALIZING.
3. **Lock scope limited to zone buttons** — The `isFinalized` flag disables create-zone and delete-zone but no other potential mutation paths (SKU assignment, measurement edits, configuration changes). The immutability contract is UI-enforced only, not store-enforced.
4. **RPC response shape unvalidated** — The store casts `data as string` without a null check. If the RPC returns null or an object, the success panel displays `undefined`. Add a type/null guard before storing.

<summary>Details</summary>

## Client-side hash and timestamp as source of truth

The `confirmFinalization` action generates a timestamp via `new Date().toISOString()` and hashes it into `computedHash` before the RPC call:

```typescript
const timestamp = new Date().toISOString();
const computedHash = await computeSha256(projectId + finalizationKey + timestamp);
```

This `computedHash` is sent as `p_computed_final_hash` to the server, and the same `timestamp` is stored in `finalizedAt` on the client. If the `finalize_project` database function uses `now()` for its own `finalized_at` column, the client displays a time that predates the actual server record by the network round-trip latency. For an immutability audit trail, this discrepancy could matter. The fix is either to return the server's `finalized_at` in the RPC response and use it for display, or to document that the client timestamp is approximate.

## Double-submit race in the confirmation dialog

The Confirm button disables itself via `disabled={isLoading}`, but `isLoading` is set inside the async `confirmFinalization` action. Between the click event and React's next render cycle, a fast second click can invoke `handleConfirm` again:

```typescript
const handleConfirm = () => {
  if (!currentProject?.id) return;
  const finalizationKey = crypto.randomUUID();
  void confirmFinalization(currentProject.id, finalizationKey);
};
```

Each invocation generates a different `finalizationKey` and `timestamp`, producing a different hash. If both RPC calls succeed, the project could be finalized twice at the database level (depending on server-side idempotency). The store itself has no guard — `confirmFinalization` doesn't check whether step is already FINALIZING before proceeding. Adding `if (get().finalizationStep === FinalizationStep.FINALIZING) return;` at the top of the action would close this window.

## Lock scope and toolbar-only enforcement

The toolbar disables zone creation and deletion:

```typescript
<button disabled={!canAddZone(zones.length) || isFinalized} ...>+ Zone</button>
<button disabled={!selection.selectedZoneId || isFinalized} ...>Delete Zone</button>
```

This is the only enforcement point. The `projectStore.removeZone` action, SKU assignment flows, or any direct store mutations from other components remain callable regardless of finalization status. The immutability contract is UI-enforced, not store-enforced. A store-level guard (checking project status before any mutation) would provide defense in depth.

## RPC response shape assumption

```typescript
const finalBomId = data as string;
```

The store casts `data` to `string` without a null check. If the RPC returns `null` (e.g., the project was already finalized and the function is a no-op), or returns an object `{ final_bom_id: "..." }`, the success panel will display garbage. The type assertion should be guarded:

```typescript
if (!data || typeof data !== 'string') {
  throw new Error('Unexpected response from finalize_project');
}
```
