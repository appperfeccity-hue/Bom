# Project finalization flow via Supabase RPC (v2)

This change implements a complete finalization workflow: a Zustand state machine store calling `finalize_project` via Supabase RPC, a three-stage confirmation UI (button → dialog → success panel), toolbar lock controls, and store-level mutation guards that block writes when the project reaches FINALIZED status. The v2 pass addresses all four issues from the prior review: double-submit guard in `confirmFinalization`, RPC response null/type validation, store-level finalization guards on all five mutation actions in `projectStore`, and documentation of the client timestamp as approximate.

Watch for: The finalization guards in `projectStore` compare against the string literal `'FINALIZED'` rather than the `ProjectStatus.FINALIZED` enum value — this works because the enum resolves to the same string, but creates a coupling to the enum's string representation that could silently break if the enum were ever refactored to numeric values (possible). The `handleConfirm` callback in the dialog still generates a new `finalizationKey` on every click, so two near-simultaneous clicks before the store guard fires would produce different keys — the store guard catches this, but only because Zustand's synchronous `get()` check runs before the first `set()` resolves in the event loop (confirmed, safe in practice).

**Verdict**: APPROVED

## High-level view

The store-level guards are the most important addition: every write action (`updateZone`, `addZone`, `removeZone`, `assignSku`, `updateMeasurements`) now early-returns when `currentProject?.status === 'FINALIZED'`, making the immutability contract store-enforced rather than UI-only. Even if a component bypasses the toolbar's disabled state, the mutation no-ops.

The double-submit guard in `confirmFinalization` checks `get().finalizationStep === FinalizationStep.FINALIZING` synchronously before proceeding. Any concurrent invocation within the same microtask sees FINALIZING and returns early.

## Store-level mutation guards and the string literal coupling

Each of the five mutation actions in `projectStore` now begins with:

```typescript
if (get().currentProject?.status === 'FINALIZED') return;
```

The string literal `'FINALIZED'` works because `ProjectStatus.FINALIZED = 'FINALIZED'`, but it's the only place in the diff where a raw string is used for status comparison. The toolbar and FinalizeButton both compare against `ProjectStatus.FINALIZED` (the enum). A refactor that changes the enum to numeric values would break the guards without a type error, since the comparison would become `string === number` and always return false — mutations would silently succeed on finalized projects.

## Test coverage gaps

Not tested: the interaction between `loadProject` and the finalization guards. A `loadProject` call that returns a non-FINALIZED status would re-enable mutations even if the project was previously FINALIZED in the client state. This means the client-side guard provides no protection against a corrupted or tampered server response.
