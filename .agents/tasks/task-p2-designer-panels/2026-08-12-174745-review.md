# Designer configuration panels for Mounting Rules, Trims, and Product Relationships

Three new CRUD panels follow the established HiddenComponents pattern: each pair (Panel + Dialog) fetches from and writes to a Supabase table, guards rendering behind `CanvasMode.DESIGNER`, and uses `fromTable` for persistence. The panels cover mounting type configuration with computed gap/structure metadata, trim SKU definitions with conditional quantity rules, and a relationship graph between template SKUs with live search and same-SKU validation. Watch for: SKU search fires on every keystroke without debounce (confirmed), delete operations ignore errors silently (confirmed), and the `or` filter in ProductRelationshipsPanel constructs a raw PostgREST filter string from user-controlled data (likely injection risk).

**Verdict**: NEEDS_CHANGES

## High-level view

The MountingRules panel pairs a pure-function lookup (`getMountingInfo`) with a form that writes to `template_lighting`. The gap/structure derivation is deterministic and lives outside the component, making it testable independently.

The Trims panel introduces conditional validation — PHYSICAL trims require a SKU, GEOMETRY trims do not — and conditional UI (fixed quantity input appears only for `TRIM_FIXED`). The concern is that `fixed_quantity` accepts negative values, with only `min={0}` on the HTML input providing a client-side constraint that doesn't block programmatic or paste input.

ProductRelationships is the most complex addition. It aggregates SKU IDs from three tables, constructs a PostgREST `.or()` filter from those IDs, and provides SKU search via `ilike`. The search effects fire on every keystroke without debounce, creating unnecessary network chatter. The `handleRemove` function does not check the delete response for errors, so a failed delete optimistically removes the item from state while the record persists in the database. The `.or()` filter interpolates SKU IDs into a raw filter string; if those IDs ever contain commas or parentheses, the filter breaks or queries unintended rows.

<details>
<summary>Issues (4)</summary>

1. **SKU search fires on every keystroke** — `AddRelationshipDialog` triggers a Supabase query on every character typed with no debounce. Add a 300ms debounce or switch to explicit search-on-enter.
2. **Delete error swallowed silently** — `handleRemove` in `ProductRelationshipsPanel` does not check the result of `.delete()`. If the delete fails (network error, RLS deny), the item vanishes from local state but persists in the database. Check `{ error }` and surface it or roll back the optimistic removal.
3. **PostgREST `.or()` filter string interpolation** — The filter `source_sku_id.in.(${skuIdArray.join(',')}),target_sku_id.in.(${skuIdArray.join(',')})` is safe only if SKU IDs are well-formed UUIDs. If IDs ever contain commas or parentheses, the filter is corrupted. Validate or quote the IDs, or use the Supabase `.in()` builder twice with separate queries merged client-side.
4. **No `fixed_quantity` parse-level guard** — The Trims dialog sends `Number(fixedQuantity)` directly. Negative values pass through; the HTML `min={0}` attribute is advisory only. Consider a `Math.max(1, ...)` guard or explicit validation before insert.

## SKU search without debounce in AddRelationshipDialog

The dialog runs two `useEffect` hooks keyed to `sourceQuery` and `targetQuery`. Each keystroke triggers a Supabase `ilike` query immediately. The cancel-flag pattern (`let cancelled = false`) prevents stale-state writes but does nothing to reduce request volume. In a panel a designer types "LED-STRIP-40" into, that's 12 queries fired within seconds. A 250-300ms debounce (via `setTimeout` cleared on re-fire) would collapse these into 2-3 round trips without degrading UX.

```tsx
// Current: fires on every character
useEffect(() => {
  if (!sourceQuery.trim()) { setSourceSkus([]); return; }
  let cancelled = false;
  const fetchSkus = async () => {
    setIsLoadingSource(true);
    const { data } = await fromTable('sku_master')
      .select('*')
      .ilike('sku_code', `%${sourceQuery}%`)
      .eq('status', 'ACTIVE')
      .range(0, 19);
    ...
  };
  fetchSkus();
  return () => { cancelled = true; };
}, [sourceQuery]);
```

## Optimistic delete without error handling

`ProductRelationshipsPanel.handleRemove` fires `.delete().eq(...)` and discards the response:

```tsx
const handleRemove = async (compatibilityId: string) => {
  await fromTable('sku_compatibility')
    .delete()
    .eq('compatibility_id', compatibilityId);
  setRelationships((prev) =>
    prev.filter((r) => r.compatibility_id !== compatibilityId)
  );
};
```

The `await` is present but `{ error }` is never destructured. If the delete fails — RLS policy denies it, network drops, constraint prevents it — the user sees the item vanish with no feedback while it persists on the server. The existing `PromotedAlternativesPanel` has the same pattern, so this is a codebase-wide convention, but it remains a fail-silent data inconsistency in this new panel.

## PostgREST `.or()` filter string construction

```tsx
const { data: compatData } = await fromTable('sku_compatibility')
  .select('*')
  .or(`source_sku_id.in.(${skuIdArray.join(',')}),target_sku_id.in.(${skuIdArray.join(',')})`);
```

The IDs in `skuIdArray` are gathered from `template_lighting`, `template_trim`, and `template_zone_sku`. These are likely UUIDs (hex and dashes only), but the filter is constructed by string concatenation without escaping. If any value contained a `)` or `,`, the PostgREST parser would misinterpret the filter boundaries. The risk is low given UUID enforcement at the DB layer, but the pattern is fragile and breaks silently if the schema ever relaxes the ID format.

## `fixed_quantity` accepts edge-case values

The Trims dialog computes:

```tsx
const fixedNum = quantityRule === 'TRIM_FIXED' && fixedQuantity ? Number(fixedQuantity) : null;
```

If `fixedQuantity` is `'-1'`, `Number('-1')` is `-1` which gets sent to the database. The HTML `<input min={0}>` prevents decrement via spinner but does not block typed or pasted negative values. Whether a fixed quantity of zero is valid depends on business rules, but a negative trim quantity is almost certainly wrong. Adding `Math.max(0, fixedNum)` or rejecting non-positive values before insert would close this.

## Test coverage gaps

The 41 new tests cover mode gating, fetch/render, badge display, conditional fields, dialog lifecycle, validation rules, and remove operations. Not tested: network error paths for fetch operations (only write errors are tested), rapid-fire query volume from the search effects, and `.or()` filter behavior with edge-case IDs.
