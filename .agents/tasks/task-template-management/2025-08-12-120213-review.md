# Template management panel for DESIGNER role

A new Zustand store and six UI components implement a "My Templates" list view for the DESIGNER role. The store (`templateManagementStore`) handles fetching the current user's templates, client-side filtering by status/search/geometry, creating DRAFT templates, retiring (archiving), duplicating, and handing off to the existing `projectStore.loadTemplate` for editing. The panel renders as a full-screen overlay triggered by a header button gated on `role === 'DESIGNER'`. Watch for: duplicate-of-duplicate naming collision (confirmed), missing input validation on dimensions (confirmed), and the "Delete" button on DRAFT templates that actually opens the retire dialog rather than performing a true delete (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The store follows the project's established Zustand pattern: state/actions/store type triple, `fromTable` helper for Supabase queries, `useAuthStore.getState()` for the current user. Filtering is synchronous and applied eagerly on every filter-setter call, keeping the full template list in memory — acceptable for a single designer's templates but worth noting if the query scope ever expands.

The component hierarchy is panel > filters + list items > dialogs, with the panel as orchestrator. The `editTemplate` action cross-coordinates three stores (`templateManagement`, `project`, `canvas`) in sequence without error handling around `loadTemplate`, which is the primary reliability gap.

The "Delete" button on DRAFT templates routes through `openRetireDialog`, meaning a draft is archived rather than actually deleted. The button label "Delete" sets an expectation of removal that the behavior doesn't match — the confirmation dialog says "retire", creating a UX mismatch.

Duplicate naming appends " (Copy)" unconditionally, so duplicating a copy yields "Name (Copy) (Copy)". Not a crash, but compounds quickly for iterative workflows.

## "Delete" vs "Retire" semantic mismatch

In `TemplateListItem.tsx`, the DRAFT branch renders a button labeled "Delete" with `data-testid="template-delete-btn"`, but its `onClick` handler calls `openRetireDialog(template)`. The retire dialog's confirmation text reads "Are you sure you want to retire **{name}**?" — a user clicking "Delete" will see the word "retire" in the confirmation, and the template will remain in the list with ARCHIVED status rather than disappearing.

```tsx
// TemplateListItem.tsx, DRAFT branch
<button data-testid="template-delete-btn" onClick={() => openRetireDialog(template)}>
  Delete
</button>
```

If soft-delete is the intended semantic, rename the button. If true deletion is intended for drafts (they have no dependents), implement a `deleteTemplate` action that issues a DELETE rather than an UPDATE.

## Duplicate naming collision

`duplicateAsNewDraft` in the store constructs the copy name as:

```ts
name: `${template.name} (Copy)`,
```

When a user duplicates "Modern Wall (Copy)", the result is "Modern Wall (Copy) (Copy)". A simple fix: strip a trailing ` (Copy)` before re-appending, or switch to a counter pattern ("Modern Wall (Copy 2)").

## Missing dimension validation

`CreateTemplateDialog` gates the submit button on `name.trim() !== '' && baseWidthMm !== '' && baseHeightMm !== ''`, but does not validate that dimensions are positive or within a sane range. A user can submit `0` or `-500` for width. The store passes these values directly to the Supabase INSERT:

```ts
base_width_mm: data.base_width_mm, // could be 0 or negative
base_height_mm: data.base_height_mm,
```

If the database has CHECK constraints these would be caught server-side with a cryptic error. Client-side validation (`> 0`, optionally an upper bound) provides a better UX.

## editTemplate error propagation

```ts
editTemplate: async (id: string) => {
  await useProjectStore.getState().loadTemplate(id);
  useCanvasStore.getState().setMode(CanvasMode.DESIGNER);
  set({ isPanelVisible: false });
},
```

If `loadTemplate` throws (network failure, template not found), the promise rejects with no catch. The error isn't surfaced in `templateManagementStore.error` — it's only in `projectStore.error`. Users see the panel frozen with no feedback. Wrapping in try/catch and setting `error` would give the panel a way to display the failure.

## Unordered fetch query

```ts
const { data, error } = await fromTable('template')
  .select('*')
  .eq('created_by', userId);
```

No `.order(...)` clause. Display order is whatever Postgres returns (heap order, effectively random after updates). Adding `.order('updated_at', { ascending: false })` ensures most-recently-edited templates appear first.

## Test coverage gaps

57 new tests cover store CRUD actions, filter logic, component rendering, button visibility per status, and dialog open/close. Not tested: `editTemplate` failure path, duplicate-of-duplicate naming, negative-dimension submission, and the actual conditional rendering of the "My Templates" button in `App.tsx` (the existing test only asserts store role state, not DOM presence).
