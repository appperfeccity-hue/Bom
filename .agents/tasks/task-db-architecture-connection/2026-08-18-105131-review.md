# Server-side RPC pipeline and frontend rewiring for DB architecture invariants

This change replaces the client-built-snapshot model with a server-authoritative pipeline: `create_project` now builds snapshots server-side, `save_actual_bom` is the only write path for actual BOM data, `generate_master_bom` resolves rule sets on the server, and `finalize_project` computes its integrity hash from persisted rows rather than accepting a client-supplied value. The frontend stores are rewired: zone/SKU mutations are in-memory only (persisted only via `save_actual_bom`'s configuration_data), the BOM pipeline uses v1/v2 snapshot mappers instead of querying non-existent tables, and the publishStore calls the RPC instead of direct inserts.

Watch for: **Finalization will always fail at runtime** — the client and server compute hashes over different data sets and with different serialization (confirmed). The v1.2.2 audit_event INSERT uses non-existent column names and will throw (confirmed). The `save_actual_bom` SKU validation omits trim SKUs, causing false rejections for any BOM with trim lines (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The snapshot creation path (`create_project`) is the strongest piece: a 5-arg SECURITY DEFINER RPC locks the template row, resolves the active rule set, assembles a complete v2 snapshot with `build_template_snapshot`, and stores a SHA-256 hash. Idempotency is handled with advisory locks. The old 6-arg client-supplies-snapshot signature is dropped.

Project isolation adds a trigger guard (`trg_project_status_guard`) that blocks direct writes to protected columns unless called from an internal RPC context or a nested trigger. The mechanism uses `SET LOCAL` session variables and `pg_trigger_depth()` which are both transaction-scoped — safe from leaking across requests.

The finalization path (`v1.2.2`) has a critical flaw: the client computes its hash from `actual_bom_line` rows (which lack `sku_code` and have different field sets), using `JSON.stringify(sortKeysDeep(...))` for serialization; the server computes from `final_bom_line` rows (which gain `sku_code` from a `sku_master` join), using PostgreSQL's `row_to_json` which outputs keys in SELECT-order not alphabetical. These will never match, making finalization permanently broken until reconciled.

The `save_actual_bom` RPC's SKU allowlist assembly omits the `trims` array from the snapshot, meaning any trim-sourced BOM line will be rejected as "not present in project snapshot."

## Finalization hash: two different computations that will never agree

The server in `v1.2.2` inserts `final_bom_line` rows by joining `actual_bom_line` with `sku_master` — gaining `sm.sku_code`, `sm.material`, etc. — then computes the hash from a `SELECT fbl.actual_bom_line_id, fbl.sku_id, fbl.sku_code, ...` over `final_bom_line`. The serialization is PostgreSQL's `row_to_json(sub.*)::text` which emits keys in the order they appear in the SELECT list:

```sql
SELECT fbl.actual_bom_line_id, fbl.sku_id, fbl.sku_code,
       fbl.product_type, fbl.quantity, fbl.required_quantity,
       fbl.waste_quantity, fbl.unit_of_measure,
       fbl.resolved_dimensions, fbl.source_zone_id,
       fbl.source_trace
FROM perfecity.final_bom_line fbl
```

The client in `finalizationStore.ts` fetches `actual_bom_line` rows (which have no `sku_code` column) and constructs:

```typescript
const subset = {
  actual_bom_line_id: line.actual_bom_line_id,
  sku_id: line.sku_id,
  sku_code: line.sku_code,       // undefined — column doesn't exist on actual_bom_line
  product_type: line.product_type,
  // ...
  source_trace: { /* client-constructed */ }
};
return JSON.stringify(sortKeysDeep(subset));  // alphabetical key order
```

Three divergences:
1. **Field values differ** — `sku_code` is `undefined`/omitted on the client, a real string on the server.
2. **Key ordering differs** — `row_to_json` uses SELECT-column-order; client uses `sortKeysDeep` (alphabetical).
3. **Data source differs** — Client reads `actual_bom_line`; server reads `final_bom_line` (which also has `source_zone_id` populated from `abl.component_id` and `source_trace` built server-side from lineage variables).

To fix: either the client must replicate the exact server computation (fetching `final_bom_line` after it's inserted — but it doesn't exist yet at call time), or the server should compute the hash from the same `actual_bom_line` input data that the client has access to, before the `final_bom_line` INSERT.

## v1.2.2 audit_event INSERT: column mismatch

```sql
INSERT INTO perfecity.audit_event (event_type, user_id, project_id, payload)
VALUES ('PROJECT_FINALIZED', p_user_id, p_project_id, jsonb_build_object(...));
```

The `audit_event` table schema (from v1.1.5 baseline):
- `actor_id UUID NOT NULL` (not `user_id`)
- `actor_role TEXT NOT NULL` (omitted)
- `event_type TEXT NOT NULL` ✓
- `entity_type TEXT NOT NULL` (omitted)
- `entity_id UUID NOT NULL` (omitted)
- `project_id UUID` ✓
- `after_state JSONB` (not `payload`)

Compare with the correct pattern from `save_actual_bom` (v1.2.0):
```sql
INSERT INTO perfecity.audit_event (
    actor_id, actor_role, event_type, entity_type,
    entity_id, project_id, after_state
) VALUES (
    p_user_id, 'CONSULTANT', 'ACTUAL_BOM_SAVED', 'actual_bom',
    v_actual_bom_id, p_project_id, jsonb_build_object(...)
);
```

## save_actual_bom: trim SKUs rejected by validation

The SKU allowlist in Step 5 builds `v_sku_set` from zones, lighting, furniture, and hidden_components but never extracts from the snapshot's `trims` array. When the BOM pipeline emits a line for a trim component, the check:

```sql
IF v_sku_set IS NOT NULL AND NOT v_sku_set @> to_jsonb(v_line ->> 'sku_id') THEN
    RAISE EXCEPTION 'SKU % not present in project snapshot', v_line ->> 'sku_id';
END IF;
```

…rejects trim SKUs. Fix by adding:

```sql
IF v_snapshot.snapshot_data -> 'trims' IS NOT NULL THEN
    SELECT COALESCE(v_sku_set, '[]'::jsonb) || COALESCE(jsonb_agg(DISTINCT t ->> 'sku_id'), '[]'::jsonb)
      INTO v_sku_set
      FROM jsonb_array_elements(v_snapshot.snapshot_data -> 'trims') t
     WHERE t ->> 'sku_id' IS NOT NULL;
END IF;
```

## Security: build_template_snapshot exposure

`build_template_snapshot` is SECURITY DEFINER and granted to all `authenticated` users with no internal role check. A CONSULTANT can invoke `build_template_snapshot(any_template_id, any_rule_set_id)` to access templates in full denormalized form. Since `create_project` (which calls it internally) already runs as SECURITY DEFINER, the direct grant is unnecessary — revoking the public EXECUTE grant and leaving it callable only from within other SECURITY DEFINER functions would tighten the surface.

## Snapshot mapper type asymmetry

`mapHiddenComponents` accepts `unknown[]` and casts internally, while `mapLighting` and `mapFurniture` use typed `TemplateLighting[]` / `TemplateFurniture[]`. This means malformed hidden component data in the snapshot is silently coerced to defaults (empty strings, 'ALWAYS' trigger type) rather than surfacing as a type error during development.

## Test coverage gaps

The SQL regression tests are structural assertions (function exists, signature matches, body contains expected patterns) rather than behavioral tests — they don't execute the RPCs against test data. The frontend store tests mock `crypto.subtle.digest` to return zeros, so hash correctness is never verified.

Not tested:
- End-to-end finalization hash agreement between client and server
- `save_actual_bom` with BOM lines containing trim SKUs
- `finalize_project` audit_event INSERT success
- `build_template_snapshot` with templates containing null optional fields
