# Server-side RPC pipeline and frontend rewiring for DB architecture invariants (v2 review)

This is the v2 pass after all five issues from the v1 review were addressed in commit 9626600. The finalization hash now computes from `actual_bom_line` on both sides using `canonical_jsonb`/`sortKeysDeep`; the audit_event INSERT uses correct columns; trim SKUs are included in the allowlist; `build_template_snapshot` lost its direct authenticated grant; and v1.2.0/v1.2.2 both use `digest(..., 'sha256')`.

Watch for: **Numeric serialization divergence between PostgreSQL JSONB and JavaScript JSON.stringify will likely cause finalization hash mismatches** for any project — the `quantity` column (DECIMAL(10,2)) is serialized as `10.00` by PostgreSQL's JSONB text output but as `10` by JavaScript (likely). **All BOM lines are persisted with `product_type = 'WALL_PANEL'`** regardless of actual component type because the pipeline output lacks a `productType` field (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The finalization hash alignment fix (Issue 1 from v1) was well-executed in principle — both sides now read the same source table (`actual_bom_line`), use the same field subset, and apply alphabetical key sorting. However, the DECIMAL(10,2) `quantity` column creates a subtle numeric representation gap: PostgreSQL's `canonical_jsonb(row_to_json(sub.*)::jsonb)::text` preserves the scale (outputting `10.00`), while JavaScript's `JSON.stringify` normalizes the number (outputting `10`). This would cause every finalization attempt to fail with a hash mismatch.

The `saveBomToServer` call maps pipeline output lines to the RPC format but omits `product_type` (the `BomOutputLine` interface doesn't carry it). The RPC defaults missing values to `'WALL_PANEL'`, so lighting, furniture, trim, and hidden component lines all get incorrectly classified. This corrupts the `actual_bom_line` data and propagates into `final_bom_line` on finalization.

The `create_project` hash in v1.1.8 still uses `pg_catalog.sha256()` while v1.2.0/v1.2.2 use `digest(... 'sha256')`. Since the snapshot hash is computed and consumed entirely server-side (never compared cross-system), this is a consistency annoyance rather than a correctness bug.

## Finalization hash: numeric scale divergence between PostgreSQL and JavaScript

The server computes the finalization hash by selecting from `actual_bom_line`:

```sql
SELECT abl.actual_bom_line_id,
       abl.sku_id,
       abl.product_type,
       abl.quantity,            -- DECIMAL(10,2), stored as e.g. 10.00
       abl.required_quantity,   -- INTEGER
       abl.waste_quantity,      -- INTEGER
       abl.unit_of_measure,
       abl.resolved_dimensions,
       abl.component_id AS source_zone_id,
       jsonb_build_object(...) AS source_trace
FROM perfecity.actual_bom_line abl
```

Then applies `canonical_jsonb(row_to_json(sub.*)::jsonb)::text`. The path is:
1. `row_to_json` serializes `quantity = 10.00` as the JSON text `10.00`
2. `::jsonb` parses it; PostgreSQL JSONB preserves numeric scale
3. `canonical_jsonb(...)::text` outputs `10.00`

On the client:
1. PostgREST returns `quantity` as a JavaScript number (losing scale info)
2. `JSON.stringify({quantity: 10})` → `"quantity":10`

The concatenated hash input differs: server has `"quantity":10.00` while client has `"quantity":10`. This produces different SHA-256 hashes for every BOM, making `finalize_project` always raise `'Finalization hash mismatch'`.

The INTEGER columns (`required_quantity`, `waste_quantity`) don't suffer this because both PostgreSQL and JavaScript serialize integers identically.

The simplest fix is the server-side cast: `abl.quantity::float8` in the hash SELECT. Double precision serializes without trailing zeros for integer values and matches JavaScript's representation for all values within safe floating-point range. Alternatively, casting to `::integer` works if quantity is always whole (the BOM pipeline only emits integers), but `::float8` is safer for future fractional quantities.

## BomOutputLine missing product_type

The `BomOutputLine` interface in `bomPipeline.ts`:

```typescript
export interface BomOutputLine {
  lineId: string;
  componentId: string;
  skuId: string;
  quantity: number;
  requiredQuantity: number;
  wasteQuantity: number;
  unitOfMeasure: string;
  calculationRule: string;
}
```

The `saveBomToServer` maps these lines without `product_type`:

```typescript
const bomLines = pipelineOutputLines.map((line) => ({
  component_id: line.componentId,
  sku_id: line.skuId,
  quantity: line.quantity,
  // ... no product_type
}));
```

The RPC's INSERT uses `COALESCE(line ->> 'product_type', 'WALL_PANEL')`, defaulting everything to `WALL_PANEL`. For projects with lighting, furniture, or trim components, the stored `actual_bom_line` rows have incorrect classification. This propagates to `final_bom_line` during finalization and corrupts downstream reporting.

## resolved_dimensions always empty

`saveBomToServer` hardcodes `resolved_dimensions: {}` for every line. Since both client and server read this from `actual_bom_line` for the finalization hash, this doesn't cause a hash mismatch — but the final BOM loses dimensional traceability. `final_bom_line.resolved_dimensions` will always be `{}`.
