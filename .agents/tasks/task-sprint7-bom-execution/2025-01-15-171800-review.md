# BOM execution pipeline and designer configuration UIs (v2)

Sprint 7 delivers a complete BOM generation pipeline: an 8-step synchronous orchestrator (`runBomPipeline`) gated by blocking validation errors, three designer-facing configuration panels (Promoted Alternatives, Consultant Permissions, Hidden Components), a consultant-facing Generate Actual BOM button wired to the store, and a structured error catalogue with 28 codes across 5 categories. All 7 issues from the v1 review have been addressed: missing geometry codes implemented, snapshot ID fixed, integration tests added, dialog error handling added, catch block now surfaces structured errors, reconciliation preserves componentId, and aspect ratio only warns when explicitly configured.

Watch for: The store catch block re-uses `GEO_WALL_DIMENSION_INVALID` as the error code for Supabase fetch failures, which mischaracterizes network/auth errors as geometry problems (confirmed). The `ValidationResultsPanel` has a fallback path for `storeError` when `pipelineErrors` is empty and status is blocked, but the current catch block always populates `pipelineErrors[0]`, making that fallback unreachable dead code (confirmed). These are non-blocking nits — the pipeline is functionally correct.

**Verdict**: APPROVED

## High-level view

The pipeline engine (`runBomPipeline`) is a pure function accepting assembled inputs and returning a result with status, lines, errors, and warnings. The store layer (`runPipeline`) performs four Supabase fetches, assembles `BomPipelineInput`, calls the engine, and maps the result to store state. This separation means the core business logic is testable without async or mocks — and the integration test suite exercises both layers.

All 19 geometry error codes now have emission paths in `validateGeometry`. The newly added 9 codes gate on optional configuration fields (`maxZoneDimension`, `minGap`, `maxGap`, `minPanelDimension`, `maxPanelDimension`, `minRetainedWidth`, `checkTotalDimensions`), which means they only fire when the designer explicitly configures limits — an opt-in model that avoids false positives on unconfigured templates.

## Catch block error code mischaracterization

In `bomStore.ts`, the `runPipeline` catch block creates a `PipelineError` with `code: ErrorCode.GEO_WALL_DIMENSION_INVALID` regardless of the actual failure:

```typescript
pipelineErrors: [{
  code: ErrorCode.GEO_WALL_DIMENSION_INVALID,
  severity: ErrorSeverity.BLOCKING,
  category: ErrorCategory.GEOMETRY,
  message: `Pipeline failed: ${errorMessage}`,
  context: { source: 'supabase_fetch', originalError: errorMessage },
}],
```

The `context.source` field carries `'supabase_fetch'`, so a consumer could distinguish this from a real geometry error by inspecting context — but the `code` and `category` fields are misleading. If downstream logic branches on `error.code === GEO_WALL_DIMENSION_INVALID` to suggest geometry-specific remediation, a network timeout would trigger that path incorrectly. The fix is trivial: add a `PIPELINE_FETCH_FAILED` code to the catalogue. Confidence: confirmed.
