# BOM execution pipeline and designer configuration UIs

Sprint 7 introduces the authoritative BOM generation pipeline: an 8-step sequential orchestrator (`runBomPipeline`) that gates output on blocking validation errors across permission, compatibility, geometry, construction, and quantity domains. Alongside the pipeline, three designer-facing configuration panels (Promoted Alternatives, Consultant Permissions, Hidden Components) and the consultant-facing Generate Actual BOM button wire the engine layer into the UI. A structured error catalogue defines 28 error codes with severity and category metadata.

Watch for: 9 of 19 geometry error codes are defined in the catalogue but never emitted by `validateGeometry` (confirmed). The `GenerateActualBomButton` passes `currentProject.id` as both `projectId` and `snapshotId`, which will query `project_snapshot` with the wrong key when the snapshot ID differs from the project ID (confirmed). No integration or E2E tests exist despite the requirements calling for them (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The store layer (`runPipeline` in `bomStore.ts`) assembles `BomPipelineInput` from four Supabase queries and then calls the synchronous `runBomPipeline`. When those Supabase fetches fail, the error message is stored in the general `error` field but never surfaced in the pipeline UI — the `ValidationResultsPanel` only reads `pipelineErrors`, which is set to `[]` in the catch path.

Nine geometry codes (TOO_LARGE, GAP_TOO_SMALL, GAP_TOO_LARGE, PANEL_TOO_SMALL, PANEL_TOO_LARGE, RETAINED_BELOW_MIN, TRIM_EXCEEDS_PANEL, TOTAL_WIDTH_MISMATCH, TOTAL_HEIGHT_MISMATCH) are registered in the catalogue but never produced by any validation function. These represent incomplete validation coverage — panel-level and total-dimension checks are simply absent.

The store integration uses `currentProject.id` as the snapshot ID. This is a placeholder assumption that breaks the moment the project has multiple snapshots or when snapshot IDs are UUIDs distinct from the project row.

The designer configuration UIs function as direct database forms with no local validation before write. All three dialogs insert rows without confirming the write succeeded, and without showing errors to the user on failure — silent data loss on RLS denial or constraint violation.

2. **Snapshot ID hardcoded to project ID** — `GenerateActualBomButton` calls `runPipeline(currentProject.id, currentProject.id)`. The second argument should be the actual snapshot ID, not the project ID. The `project_snapshot` query filters on `snapshot_id`, so this will fail when they diverge.
3. **No integration/E2E tests** — The requirements explicitly call for integration tests covering the complete pipeline. Only unit tests with mocked engines exist. There are no tests that exercise `runPipeline` through the store with realistic (even mocked) Supabase responses.
4. **Dialog writes ignore errors** — `AddPermissionDialog`, `AddAlternativeDialog`, and `AddHiddenComponentDialog` all `await fromTable(...).insert(...)` but never check the returned `{ error }`. On failure the dialog closes and calls `onAdded()`, giving the user no indication the write failed.
5. **Catch block loses structured errors** — When the `runPipeline` store action catches a thrown `Error` (from Supabase fetch failures), it sets `pipelineErrors: []` and only stores the message as `error: string`. The `ValidationResultsPanel` reads `pipelineErrors` to display issues, so Supabase failures produce a BLOCKED state with an empty error list and an invisible error message.
6. **Reconciliation merges componentId** — `reconcileBomLines` merges lines by `skuId + calculationRule` key, but the resulting merged line retains only the first `componentId` and `lineId`. After merging two panel zones with the same SKU, the output line references a single zone ID, losing traceability to the second zone.
7. **Implicit default aspect ratio** — `GEO_ZONE_ASPECT_RATIO` warns on ratios above 10 even when no explicit limit is configured (the default `maxAspectRatio` of 10 in `validateGeometry` fires whenever `maxAspectRatio` is not set in `BomConfiguration`). Production use may trigger unexpected warnings for intentionally tall/narrow zones.

## Site adaptation error mischaracterization

The site adaptation step is wrapped in a try/catch because the underlying `adaptZonesToSite` engine throws `EngineError` on invalid dimensions. The pipeline converts any thrown error into a `GEO_WALL_DIMENSION_INVALID` pipeline error regardless of cause. If `adaptZonesToSite` ever throws for a non-dimension reason (e.g., a calculation overflow in proportional scaling), the error will be mischaracterized as an invalid wall dimension.

## Incomplete geometry validation coverage

The error catalogue defines 19 geometry codes. `validateGeometry` emits only 10:

```
Emitted:     GEO_WALL_DIMENSION_INVALID, GEO_ZONE_COUNT_EXCEEDED,
             GEO_ZONE_NEGATIVE_DIMENSION, GEO_ZONE_INVALID_POSITION,
             GEO_ZONE_MIN_DIMENSION, GEO_ZONE_TOO_SMALL,
             GEO_ZONE_EXCEEDS_WALL, GEO_ZONE_OUTSIDE_WALL,
             GEO_ZONE_ASPECT_RATIO, GEO_ZONE_OVERLAP

Never emitted: GEO_ZONE_TOO_LARGE, GEO_GAP_TOO_SMALL, GEO_GAP_TOO_LARGE,
               GEO_PANEL_TOO_SMALL, GEO_PANEL_TOO_LARGE,
               GEO_RETAINED_BELOW_MIN, GEO_TRIM_EXCEEDS_PANEL,
               GEO_TOTAL_WIDTH_MISMATCH, GEO_TOTAL_HEIGHT_MISMATCH
```

The unimplemented codes fall into two groups: gap/panel-level checks that require panel dimension data (which `validateGeometry` doesn't receive — it only gets zone-level `x/y/width/height`), and total-dimension consistency checks that would require summing zone widths/heights and comparing against wall dimensions. A zone with panels whose individual dimensions exceed the panel spec will pass geometry validation uncaught.

## Store integration: snapshotId and error propagation

`GenerateActualBomButton` calls `runPipeline(currentProject.id, currentProject.id)`. The store action queries `project_snapshot` with `.eq('snapshot_id', snapshotId)`. The API signature accepting separate `projectId` and `snapshotId` arguments implies they can diverge, but the UI never resolves which snapshot to use.

When the Supabase fetches in `runPipeline` fail, the catch block sets `pipelineStatus: 'blocked'` with `pipelineErrors: []` and stores the raw error message in the store's general `error` field. The `ValidationResultsPanel` reads `pipelineErrors` for display, so a network failure results in a BLOCKED badge with no listed errors and no explanation visible to the consultant.

## Designer configuration panels: fire-and-forget writes

All three dialogs follow the same pattern:

```typescript
await fromTable('...').insert({ ... });
onAdded();
```

The `insert` return value `{ error }` is never inspected. If the write fails (network error, RLS denial, constraint violation), the dialog closes, the parent calls `fetchData()` to refresh, and the user sees no new row — with no error message explaining why.

## Reconciliation traceability gap

`reconcileBomLines` merges lines by `${skuId}-${calculationRule}` key. When two zones use the same SKU and both produce WALL_PANEL lines, the merge keeps the first line's `lineId` and `componentId` while summing quantities. The downstream consumer of `BomOutputLine` can no longer trace which zones contributed to the merged quantity. If the final BOM needs per-zone breakdown for installation instructions, this information is lost at reconciliation.

## Test coverage gaps

Not tested:
- Integration of `runPipeline` through the store (the store test mocks `runBomPipeline` rather than exercising it)
- The 9 unimplemented geometry error codes
- Dialog error handling on Supabase write failures
- Pipeline behavior when `adaptZonesToSite` throws for reasons other than invalid dimensions
- The interaction between `ValidationResultsPanel` and the store's `error` field when Supabase fetches fail
