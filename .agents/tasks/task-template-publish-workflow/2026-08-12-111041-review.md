# Template Publishing Workflow (v2)

A 4-step wizard (Validate, Generate Master BOM, Approve, Publish) driven by a Zustand state machine. This iteration addresses the five issues raised in the v1 review: template status is now synced to projectStore after publish, a server-side validation note warns about additional eligibility checks, the BOM engine note explains empty lines are populated separately, re-run validation buttons provide backward navigation, and the approval action includes RLS authorization commentary with enhanced permission-denied error handling.

Watch for: `rerunValidation` clears BOM state but never cleans up the previously inserted `master_bom` row in the database — orphan rows accumulate on repeated generate-then-rerun cycles (likely). Error handling during BOM generation and approval still lacks a retry path; only the final publish step surfaces a retry button (confirmed).

**Verdict**: APPROVED

## High-level view

All five v1 issues have been addressed. No blocking concerns remain.

The remaining architectural asymmetry is error recovery: a failure in `generateMasterBom` or `approveMasterBom` dumps the user to a generic ERROR screen with only a close button, forcing a full restart. The publish step has retry; the earlier steps do not. This is a UX gap rather than a functional bug.

One new concern introduced by `rerunValidation`: it clears `generatedBom` and `generatedBomLines` from local state but does not delete or invalidate the `master_bom` row already inserted into Supabase. If the user re-runs validation and then generates a new BOM, a second row is inserted. Whether this matters depends on whether the DB has a unique constraint on `(template_id, status='GENERATED')` or whether multiple generated BOMs per template are acceptable by design.

## Orphaned BOM rows from re-run cycles

`rerunValidation` resets local state and calls `runValidation`:

```ts
rerunValidation: async (templateId: string) => {
  set({
    generatedBom: null,
    generatedBomLines: [],
    error: null,
  });
  await usePublishStore.getState().runValidation(templateId);
},
```

If a user already clicked "Generate Master BOM" (which inserts a row into `master_bom` with `status: 'GENERATED'`), then clicks "Re-run Validation" from the ApprovalStep, the local reference is cleared but the database row persists. If validation passes again and the user generates a new BOM, a second insert occurs. Over time, this creates orphan rows in `master_bom` for every abandoned generation cycle.

The schema doesn't appear to have a unique constraint on `(template_id, status)` that would prevent this.

## Error recovery asymmetry

The `PublishWorkflow.tsx` error branch only offers a close button:

```tsx
case PublishStep.ERROR:
  return (
    <div style={{ padding: '16px' }}>
      ...
      <button onClick={reset}>Close</button>
    </div>
  );
```

A transient network error during BOM generation forces the user to start over from validation. The retry pattern from `PublishConfirmation` could be extended: store the step that failed and offer a context-aware retry.

## V1 issues — resolution status

All five addressed: (1) server-validation note in ValidationResultsPanel, (2) RLS comment + permission-denied error handling with tests, (3) BOM engine note in ApprovalStep, (4) projectStore status sync to ACTIVE after publish with test, (5) rerunValidation action with buttons in both ValidationResultsPanel and ApprovalStep.

## Test coverage gaps

Not tested: the orphan BOM scenario (re-run after generate, then generate again — no assertion that the first row is cleaned up). Not tested: behavior when `currentTemplate` is null and the store action receives a template ID directly (UI guards exist but the store itself would attempt the Supabase call).
