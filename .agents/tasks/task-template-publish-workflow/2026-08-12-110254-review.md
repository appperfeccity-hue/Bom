# Template Publishing Workflow — 4-Step Wizard

A new Zustand store and wizard UI implement the template publish lifecycle: validate template readiness, generate a master BOM, approve it, then publish (set template to ACTIVE). The store drives a linear state machine through ten steps, gating progression on Supabase responses. The UI is a fixed overlay panel rendered conditionally from App.tsx, with the entry point being a "Publish Template" button visible only in DESIGNER mode for DRAFT templates.

Watch for: Client-side validation covers only zone SKU status but the DB trigger also validates lighting, furniture, trim, and hidden component SKUs — a template can pass all five client gates yet still be rejected by `trg_template_before_activate` (confirmed). The approval step writes `approved_by` but never verifies the user has the authority to approve (likely). BOM generation inserts a record with no lines, then immediately transitions to the approval step — the "Master BOM" being approved is effectively an empty shell (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The state machine is a linear enum (`PublishStep`) with no backward transitions. Error recovery exists only at the final publish step (retry button); errors during BOM generation or approval dump the user to a generic ERROR screen with just a close button and no path forward without restarting.

Client-side validation checks five gates (zone SKU assignment, SKU/catalogue status, zone overlaps, boundary constraints, metadata) but the server-side trigger checks six categories of SKU eligibility (zones, zone alternatives, lighting, furniture, trim, hidden components) plus requires an approved BOM. The partial client validation creates a false confidence gap: users who pass all five gates may still face a trigger rejection at the final step.

BOM generation inserts a `master_bom` row with status GENERATED but never populates `master_bom_line` rows. The approval step shows "No BOM lines generated" and lets the user approve anyway. Whether this is intentional scaffolding (engine populates lines later) or a gap depends on the intended architecture, but the UX presents it as a complete approval checkpoint.

After a successful publish, `projectStore.currentTemplate.status` is never updated to ACTIVE — the toolbar button stays visible until the next data fetch, allowing a redundant re-publish attempt (caught by the trigger, but confusing).

1. **Validation scope gap vs DB trigger** — Client validation checks zone SKUs only; the DB trigger also validates lighting, furniture, trim, and hidden component SKUs. A template can pass client validation and fail at publish. Either expand client gates or surface this limitation in the validation results panel.
2. **No authorization check on BOM approval** — `approveMasterBom` writes the current user's ID as `approved_by` without verifying role/permission. Any authenticated user can approve.
3. **Empty BOM approval** — `generateMasterBom` creates a BOM record with zero lines, then the user immediately approves it. If line generation is deferred to an engine, the UI should indicate this; otherwise, users are approving an empty artifact.
4. **Template status not synced after publish** — After `publishTemplate` succeeds, `projectStore.currentTemplate.status` remains DRAFT. The publish button stays visible until the user navigates away or refetches.
5. **No backward step navigation** — If validation passes but the user wants to re-check after making changes (e.g., opened the panel, left it open, edited zones), there's no way to re-run validation without closing and reopening the panel.

## Validation scope mismatch with `check_template_eligible`

The DB trigger function `check_template_eligible` queries six entity categories before allowing activation:

```
template_zone / template_zone_sku (primary SKU)
template_zone_alternative (active alternatives)
template_lighting
template_furniture
template_trim
template_hidden_component (mandatory ones)
```

The client-side `runValidation` only checks the first category (zone primary SKUs via the `zoneSku` map) and catalogue status. A template with all zones correctly assigned but a lighting fixture pointing to a discontinued SKU will pass all five client gates, proceed through BOM generation and approval, then fail at the publish step with a generic trigger error.

This is a confirmed gap: the trigger SQL calls `check_template_eligible(NEW.template_id)` which checks all six categories, while `publishStore.runValidation` only queries `catalogue_entry` for SKU IDs extracted from `zoneSku.values()`.

The fix is either to expand the client validation to also check lighting/furniture/trim/hidden-component SKUs (they're already in `projectStore` state as `lighting`, `furniture`, `trims`), or to add a warning in the validation results that server-side eligibility checks may still reject activation.

## Empty BOM as approval artifact

`generateMasterBom` inserts a `master_bom` row:

```ts
const { data, error } = await fromTable('master_bom')
  .insert({
    template_id: templateId,
    status: 'GENERATED',
    engine_version: '1.0',
    rule_set_id: 'default',
    generated_at: new Date().toISOString(),
  })
  .select()
  .single();
```

It never queries or inserts `master_bom_line` rows. The store sets `generatedBomLines: []` and immediately transitions to `BOM_GENERATED`, enabling the approval button. If the engine is a separate process that populates lines asynchronously, then the wizard shouldn't transition to approval until lines exist. If lines are intentionally deferred past approval, the UX should make this explicit rather than showing an empty table with a ready-to-approve button.

## Local state drift after publish

After `publishTemplate` succeeds, the store transitions to `PUBLISHED` but never updates `projectStore.currentTemplate.status`. The toolbar check `currentTemplate?.status === TemplateStatus.DRAFT` remains true, so the "Publish Template" button stays visible. Clicking it again would attempt to publish an already-active template — caught by the error handler, but a confusing user experience. Either update local state after success or trigger a refetch.

## Approval authorization

`approveMasterBom` reads the current user's ID from `useAuthStore.getState().user?.id` and writes it to `approved_by`. There's no guard ensuring the user holds an approval-authorized role. If Supabase RLS policies enforce this server-side, the client provides no indication that an unauthorized user would be blocked, and no graceful error handling specific to a permissions denial.

## Error handling asymmetry

The `PublishConfirmation` component handles the ERROR step with a retry button, but only when the error occurs during the publish step itself. If `generateMasterBom` or `approveMasterBom` fails, the store enters `PublishStep.ERROR` and the `PublishWorkflow` renders a generic error panel with only a "Close" button — no retry, no way to resume from the last successful step.

## Test coverage gaps

Not tested: the scenario where validation passes client-side but the publish trigger rejects (end-to-end mismatch). Not tested: what happens when `useAuthStore.getState().user` is null during `approveMasterBom` (the `userId` would be `undefined`, written to the DB as null).
