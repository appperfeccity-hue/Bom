# Integration Validation Matrix: 121 tests across the full BOM production chain

This change adds a dedicated `frontend/src/__integration__/` directory containing 10 test files and 2 helper modules that exercise every step of the BOM pipeline—from template snapshot assembly through geometry/SKU/permission validation, quantity calculation, BOM reconciliation, and persistence round-tripping. The tests operate entirely against pure engine functions with realistic fixture data (no network calls, no Supabase mocks). The approach validates a critical invariant: that canvas state, rule-engine state, BOM state, and persisted snapshot all describe the same physical wall.

Watch for: the bidirectional sync assertion helper (`assertBomConsistency`) silently skips hidden components whose trigger evaluates to `false`, which means a hidden component that *should* fire but doesn't won't be caught by the "no orphans" check (confirmed). The 50mm retained-width pipeline test relies on a carefully constructed fixture (110mm zone, 100mm panel, 12mm gap) that passes the 100mm `minZoneDimension` default only because it's slightly above threshold—this is fragile to any change in the default (likely).

**Verdict**: APPROVED

## High-level view

The test suite is structured as 10 numbered files mapping 1:1 to the validation matrix areas. A shared `helpers/fixtures.ts` provides factory functions for five standard scenarios, while `helpers/pipelineHelpers.ts` provides `assertBomConsistency` and `assertNoStaleReferences` as reusable invariant checks. The `assertBomConsistency` helper has an asymmetry: it verifies zones→WALL_PANEL, lighting→LIGHT, and furniture→FURNITURE in the forward direction, but only checks hidden components in the reverse direction (no orphans). This means a regression that silently drops a hidden component won't be caught by the helper.

The permission/consultant tests verify the pipeline's early-exit gate: when `consultantActions` is non-empty, permissions are checked first and block the pipeline if violated; when empty or absent, the check is skipped. The "no bypass" tests confirm that an empty permissions array means "no restrictions" rather than "deny all."

All fixtures use `templateWallWidth === wallWidth`, meaning site adaptation is always a no-op. The suite deliberately focuses on post-adaptation steps, but the site adaptation engine (proportional scaling, locked zones, min/max clamping) has zero integration coverage here.

The E2E scenarios triangulate by running `runBomPipeline` and cross-checking results against both the snapshot (via `assertBomConsistency`) and independent engine calls (e.g., calling `calculateWallPanels` directly). If pipeline wiring drifts from individual engines, the E2E tests catch it.

## Consistency assertion gap for hidden components

The `assertBomConsistency` helper in `pipelineHelpers.ts` checks three categories of components: zones with panels map to WALL_PANEL lines, lighting maps to LIGHT lines, and furniture with `quantity > 0` maps to FURNITURE lines. For hidden components, it only checks the reverse direction—every BOM line must trace back to *some* snapshot component. It does not independently verify that hidden components whose trigger *should* evaluate to `true` actually produced a line.

This means if `calculateHiddenComponent` has a regression that causes a CONDITION trigger to incorrectly return `included: false`, the consistency helper will not flag it. The individual test in `05-bomGeneration.test.ts` (which checks `hidden-clip` quantity equals 12) provides partial coverage, but only for one fixture. A systematic check that mirrors the CONDITION evaluation and asserts the expected count of HIDDEN_COMPONENT lines would close this gap.

## Retained-width test depends on implicit geometry defaults

In `07-validationErrors.test.ts`, the test "pipeline blocks when retained width would be below 50mm" constructs a zone 110mm wide with 100mm panels and 12mm horizontal gap. The arithmetic: N=2 panels, span=212mm, trim_per_side=51mm, retained=49mm < 50mm → `EngineError`. The pipeline catches this and returns `BLOCKED` with `QTY_PANEL_NO_VALID_ARRANGEMENT`.

The zone width of 110mm passes geometry validation because the engine's default `minZoneDimension` is 100mm. If that default were raised to 150mm, the test would fail with `GEO_ZONE_MIN_DIMENSION` instead of the intended error code. Setting `configuration.minZoneDimension = 50` explicitly in the input would decouple the test from the default.

## Coverage of trigger exclusion paths

The hidden component tests verify three positive triggers:
- `ALWAYS` → included (bracket, quantity = 4)
- `CONDITION` with `zone_count GTE 3` and `fieldValues.zone_count = 4` → included (clip, quantity = 12)
- `DEPENDENCY` with `parentPresent = true` → included (adhesive, quantity = 8)

No test verifies the negative cases within the full pipeline context:
- `CONDITION` where `fieldValues` don't meet the condition → should produce 0 HIDDEN_COMPONENT lines for that ID
- `DEPENDENCY` where `parentPresent = false` → same

A hidden component that is correctly excluded should not appear in `actualBomLines`, and the test should assert its absence.

## Not tested

- Site adaptation with `wallWidth !== templateWallWidth` (proportional scaling, locked zones, min/max clamping)
- Furniture quantity boundary violations through the pipeline (quantity < min or > max throw `EngineError`, but no integration test drives this to a `BLOCKED` result)
- Construction rules beyond COVE structure requirement (invalid mounting types, missing mandatory components via the pipeline)
- Multiple simultaneous validation failures (e.g., both geometry error AND compatibility error—only the first blocking stage is tested due to sequential pipeline design)
