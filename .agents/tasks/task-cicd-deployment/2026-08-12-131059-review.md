# CI/CD pipeline and Docker deployment for React/Vite SPA

This change adds the full deployment pipeline for the frontend: a GitHub Actions CI workflow (lint, typecheck, test, build), a deploy workflow targeting GitHub Pages via `workflow_run`, a multi-stage Dockerfile with nginx, chunk splitting in the Vite build config, and developer-experience scaffolding (Makefile, docker-compose, env example, README docs). Watch for: deploy workflow rebuilds from scratch instead of reusing CI artifacts (confirmed); Docker `env_file` has no effect because Vite bakes env vars at build time, making the docker-compose env_file misleading (confirmed); deploy workflow has no fallback for missing `vars` so a misconfigured repo produces a broken build silently (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The CI workflow gates merges with four parallel-then-sequential jobs and handles the missing ESLint config gracefully. The build job provides a sensible fallback for Supabase vars (`placeholder` values) so CI doesn't break on forks, but the deploy workflow does not, creating an asymmetry where the deploy can embed empty strings into the production bundle without failing.

The Dockerfile is a clean two-stage build/serve pattern, but there's a conceptual mismatch in the docker-compose setup: it passes an `env_file` to the runtime container, but Vite embeds env vars at build time via `import.meta.env`. The nginx container never reads those vars, so the compose config creates a false impression that runtime env injection works.

The deploy workflow rebuilds the app from source rather than downloading the artifact produced by CI. This means two identical `npm ci && npm run build` executions per push to main, adding ~2 minutes of wall time and creating a window where CI and deploy could produce different bundles if a dependency updates between runs.

1. **Deploy vars missing fallback** — `deploy.yml` uses `${{ vars.VITE_SUPABASE_URL }}` without a fallback. If the repo variable is unset, Vite embeds an empty string and the deployed app silently fails to connect. Add a validation step or provide fallback + warning like CI does. (confirmed)

Either pass build-args to the Dockerfile or document that the env_file only matters if the Dockerfile is rebuilt via compose. (confirmed)
3. **Redundant rebuild in deploy** — `deploy.yml` re-runs `npm ci && npm run build` instead of downloading the `frontend-dist` artifact already uploaded by CI. This wastes time and risks divergence. (confirmed)
4. **No `base` path for GitHub Pages** — If the repo is deployed under a subpath (e.g., `https://user.github.io/Bom/`), Vite needs `base: '/<repo>/'` in the config or as a build arg. Currently no mechanism for this exists; deployment will 404 on assets if the repo isn't a user/org root site. (likely)
5. **`make lint` will fail without ESLint config** — The Makefile `lint` target runs `npm run lint` unconditionally, while the CI workflow gracefully skips lint when no config is found. A developer running `make lint` locally hits an ESLint error. (confirmed)

## Deploy workflow: silent failure on missing vars

The CI build job provides inline fallbacks:

```yaml
VITE_SUPABASE_URL: ${{ vars.VITE_SUPABASE_URL || 'https://placeholder.supabase.co' }}
```

The deploy workflow does not:

```yaml
VITE_SUPABASE_URL: ${{ vars.VITE_SUPABASE_URL }}
```

If a repo maintainer forgets to set the variable, the deploy succeeds (Vite doesn't error on empty env vars) and ships a bundle that silently fails at runtime. Since `supabase.ts` falls back to `http://localhost:54321` when the env is undefined, a deployed Pages site would attempt to connect to localhost — failing silently for users. A pre-build validation step (`if [ -z "$VITE_SUPABASE_URL" ]; then echo "::error::..." && exit 1; fi`) would catch this.

## Docker env_file mismatch

`docker-compose.yml` declares:

```yaml
env_file:
  - ./frontend/.env
```

This injects environment variables into the running container's process environment. But the served content is static HTML/JS built by Vite during `docker build`. The nginx process doesn't read `VITE_*` vars. The env_file line does nothing useful in this configuration. Two paths to fix: (1) document that `docker compose build` must be re-run when env changes, or (2) switch to a runtime env injection pattern (e.g., an entrypoint script that writes a `config.js` read by the app at runtime).

## Redundant build in deploy workflow

The CI workflow uploads `frontend-dist` as an artifact. The deploy workflow ignores this and rebuilds from scratch. `workflow_run` triggers asynchronously — if a transient npm registry issue or dependency drift occurs between the CI run and the deploy run, the deploy could fail or produce a subtly different bundle. Downloading the artifact from the triggering workflow run via `actions/download-artifact` with `run-id` would be more reliable and faster.

## GitHub Pages base path

Vite defaults `base` to `'/'`. If this repository is deployed to `https://<org>.github.io/Bom/`, all asset paths will resolve against the domain root and 404. The fix is setting `base` in `vite.config.ts` or passing it as a build-time env var. Worth adding a configurable `VITE_BASE_PATH` or documenting the assumption that this deploys to a root site.

## Makefile lint target asymmetry

The CI `lint` job includes a shell conditional to skip lint when no ESLint config exists. The Makefile `lint` target calls `npm run lint` directly, which runs `eslint .` and fails if no config is present (ESLint 9 flat config requires an explicit config file). Adding the same guard to the Makefile or creating an `eslint.config.js` would align local and CI behavior.
