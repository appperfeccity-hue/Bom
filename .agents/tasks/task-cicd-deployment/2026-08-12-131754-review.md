# CI/CD pipeline and Docker deployment for React/Vite SPA (v2)

This change adds the full deployment pipeline for the frontend: GitHub Actions CI (lint, typecheck, test, build with artifact upload), a deploy workflow targeting GitHub Pages via `workflow_run` with artifact reuse, a multi-stage Dockerfile with nginx, chunk splitting in Vite, and developer-experience scaffolding (Makefile, docker-compose with build args, env example, README). All five issues from the v1 review have been addressed: deploy vars are validated before use, docker-compose uses build args instead of runtime env_file, the deploy workflow reuses CI artifacts via `download-artifact@v4` with `run-id`, the base path is configurable via `VITE_BASE_PATH`, and the Makefile lint target includes the same ESLint config guard as CI. Watch for: deploy workflow validates Supabase vars it no longer uses — the artifact carries vars baked during CI, creating a gap if CI used placeholders (confirmed); `make docker-run` passes `--env-file` to an nginx container that never reads those vars (confirmed).

**Verdict**: APPROVED

## High-level view

The CI-to-deploy handoff downloads the pre-built artifact from the triggering CI run, eliminating the redundant rebuild. The env var validation step in deploy now validates variables that aren't consumed by that workflow — the artifact's Supabase config was determined at CI build time, not deploy time. On a repo where vars are added after CI has already run with placeholders, the deploy would correctly block, but the user would need to re-trigger CI to produce a correctly-configured artifact.

The `make docker-run` target passes `--env-file ./frontend/.env` to the nginx runtime container, which doesn't read process environment. The docker-compose file uses `build.args` correctly, but the Makefile run target creates a false impression that runtime env injection works.

## Deploy var validation mismatch

The deploy workflow structure after the v1 fix:

```yaml
env:
  VITE_SUPABASE_URL: ${{ vars.VITE_SUPABASE_URL }}
  VITE_SUPABASE_ANON_KEY: ${{ vars.VITE_SUPABASE_ANON_KEY }}
steps:
  - name: Validate required environment variables
    run: |
      if [ -z "$VITE_SUPABASE_URL" ]; then ...
  - uses: actions/download-artifact@v4
    with:
      run-id: ${{ github.event.workflow_run.id }}
```

The artifact was produced by CI's build job, which used `${{ vars.VITE_SUPABASE_URL || 'https://placeholder.supabase.co' }}`. If vars are not set at CI time, CI builds with placeholders (no failure — it has fallbacks). The deploy workflow then validates, *fails* because vars are empty, and blocks the deploy. The deploy correctly prevents shipping placeholder config, but the error message implies the fix is to "configure repository variables" — which won't retroactively fix the already-built artifact. The user would need to re-trigger CI after setting vars. Moving validation to CI's build job (fail if vars are empty and the trigger is `push` to `main`, allow placeholders on PRs) would surface the failure earlier.

## Makefile docker-run env-file

```makefile
docker-run:
	docker run --rm -p 8080:80 --env-file ./frontend/.env bom-frontend
```

The `--env-file` flag sets environment variables in the container's shell environment. The nginx process doesn't read them, and the static JS files don't reference `process.env` at runtime. The flag misleads developers into thinking they can change Supabase config without rebuilding the image.
