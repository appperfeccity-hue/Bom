# Konva dual-mode canvas with Zustand state and Supabase persistence (v2)

All seven issues from the v1 review are addressed. Autosave routes through the debouncer, overlap detection gates creation/drag/resize/panel edits, resize handles respond to pointer events, the properties panel validates through constraints, auth state subscribes on mount, fitToViewport is guarded by initialization refs, and the ZonesLayer void-index suppression is gone.

Two new concerns emerge from the fix commit itself: the single-slot `pendingZoneUpdate` pattern can silently drop persistence for earlier zone updates within the debounce window, and `useZoneCreate.handleCreateEnd` reads `zones` for overlap checking but its dependency array only tracks `zones.length`, creating a stale-closure risk.

Watch for: multi-zone update loss through the single-slot debouncer (confirmed); stale zone positions in the create overlap check when zones move without count changing (confirmed).

**Verdict**: NEEDS_CHANGES

---

## High-level view

The autosave integration correctly transitions `saveStatus` through the `unsaved → saving → saved | error` state machine and debounces rapid mutations. However, the single module-level `pendingZoneUpdate` variable means only the *last* zone updated within a debounce window gets persisted to Supabase — earlier zone updates are optimistically reflected in UI but silently dropped from the database.

The overlap enforcement is comprehensive — every mutation path (create, drag, resize, properties panel) now checks `hasOverlap` before committing. The create hook has a stale-closure issue: its dependency array is `[isCreating, createPreview, currentTemplate, zones.length, addZone]` but it reads the full `zones` array for overlap, meaning zone position changes that don't affect count leave the callback using old positions.

## Single-slot pendingZoneUpdate drops concurrent updates

The autosave wiring stores the persistence closure in a single module-level variable:

```ts
let pendingZoneUpdate: (() => Promise<void>) | null = null;

// Inside updateZone:
pendingZoneUpdate = async () => {
  const { error } = await fromTable('template_zone')
    .update({ ... })
    .eq('id', zone.id);
  ...
};
saver.debouncedSave(useCanvasStore.getState().version);
```

When the debounce fires, `createDebouncedSave` calls `saveFn(version)`, which runs `pendingZoneUpdate()` and clears the slot. If two different zones are updated within the 2-second window — zone A at t=0, zone B at t=1s — zone B's closure replaces zone A's. The debounce fires at t=3s and only persists zone B. Zone A stays updated in Zustand state but never reaches Supabase.

The rollback closure also captures `prevZones` from the moment of the call. If zone B's persist fails, it rolls back to the state before B — which includes zone A's optimistic change in local state. But zone A was never persisted, creating divergence.

Fix: replace the single slot with a `Map<string, () => Promise<void>>` keyed by zone ID. When the debounce fires, iterate the map and execute all pending closures (or batch them into a single RPC call).

## Stale closure in useZoneCreate.handleCreateEnd

```ts
const handleCreateEnd = useCallback(() => {
  // ...
  if (hasOverlap(newBox, zones)) { ... }
  // ...
}, [isCreating, createPreview, currentTemplate, zones.length, addZone]);
```

`zones` is captured from the render where `useCallback` was last re-created. The dependency array only re-creates the callback when `zones.length` changes. If an existing zone was dragged to a new position (same count, different coordinates), `handleCreateEnd` still sees the old positions. A user could create a zone that overlaps with a recently-moved zone because the overlap check runs against stale data.

The fix is straightforward: change `zones.length` to `zones` in the dependency array. The same pattern is already used correctly in `useZoneDrag` and `useZoneResize`.
