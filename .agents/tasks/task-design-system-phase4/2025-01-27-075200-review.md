# Phase 4 Design System: Animations, Accessibility, and Responsive Layout

CSS-only design system extension adding motion, accessibility landmarks, and responsive breakpoints to the Perfeccity shell. Two new CSS files (`animations.css`, `responsive.css`) handle motion and layout adaptation, while ARIA attributes are added to existing layout and modal components. Loading states use a CSS shimmer gradient, and a `prefers-reduced-motion` media query disables all motion globally. Watch for: focus trap is missing from dialogs despite `aria-modal="true"` (confirmed), the 1280px and 1024px responsive rules conflict on `.panel-left` visibility (confirmed), and `aria-live="assertive"` elements mount with content already present which may cause unexpected announcements if rendering is refactored to show/hide (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The animation system stays at or under 150ms for all interaction transitions, with only the shimmer loop running longer at 1.5s. The `prefers-reduced-motion` block covers all animations and transitions declared in the file.

Accessibility additions cover landmarks (nav, main, status, banner) and dialog semantics, but stop short of implementing focus trapping. Every dialog now declares `aria-modal="true"`, which tells assistive technology that content behind the dialog is inert — but without a corresponding focus trap, keyboard users can still tab into the background, breaking the contract `aria-modal` establishes.

The responsive CSS introduces a conflict: at 1280px, `.panel-left` is set to `display: none`, but at 1024px it's set back to `display: block` with fixed positioning. Since both queries match below 1024px, the 1024px rule wins by source order, making the panel reappear as a fixed overlay. Between 1024px and 1280px, the panel is hidden with no toggle mechanism to access it.

## Focus trap gap on dialog components

BomPanel, ProjectCreationWizard, FinalizationConfirmDialog, and TemplateManagementPanel all received `role="dialog"` and `aria-modal="true"`. The ARIA spec for `aria-modal` states that "content outside the dialog is inert." Assistive technology uses this signal to restrict virtual cursor navigation, but keyboard focus is not managed by ARIA — it requires JavaScript. Without a focus trap, a keyboard user pressing Tab will move focus behind the dialog into the icon rail or status bar, contradicting the `aria-modal` promise.

The fix is either:
- Add a JS focus trap (a `useEffect` that constrains Tab/Shift-Tab within the dialog container and returns focus to the trigger on close), or
- Use the native `<dialog>` element which provides trapping for free, or
- Remove `aria-modal="true"` and accept that these panels are non-modal overlays (which matches their current keyboard behavior).

Since the task scope is "CSS + ARIA attributes only, no business logic," a proper focus trap may be intentionally out of scope. If so, `aria-modal` is the wrong attribute to add without the accompanying behavior; `role="dialog"` alone (without `aria-modal`) would be honest about the current state.

## Responsive breakpoint cascade conflict

```css
/* 1280px rule */
@media (max-width: 1280px) {
  .panel-left { display: none; }
}

/* 1024px rule */
@media (max-width: 1024px) {
  .panel-left {
    display: block;
    position: fixed;
    ...
  }
}
```

At a 900px viewport, both queries match. The 1024px block comes later in source order, so `.panel-left` gets `display: block` + fixed positioning. But between 1024px and 1280px, the panel is simply hidden with no way to access it — there's no toggle button or gesture to summon it. If a user needs the left panel's content at 1100px, it's inaccessible.

## Animation timing inconsistency

The existing design system defines `--transition-fast: 120ms ease` and `--transition-normal: 200ms ease`. The new `animations.css` hard-codes `100ms ease` for button hover and input focus transitions rather than referencing these custom properties. This creates two competing timing scales: icon rail items use `var(--transition-fast)` from `layout.css` while buttons use a raw `100ms` from `animations.css`. Consolidating on the custom properties would prevent drift if the timing scale is adjusted later.

## Status bar live region chattiness

`role="status"` + `aria-live="polite"` is applied to the entire `.status-bar` div, which contains the snapshot hash, engine status, and error count. Any text change across all these spans triggers a screen reader announcement. The save-status element cycles through "saving…" → "saved" on every autosave — this will generate frequent interruptions. Scoping the live region to just the save-status span (or the error count) would reduce noise.

## Skeleton shimmer on text content

The `.skeleton-shimmer` class applies a sweeping gradient background. When applied to the BomPanel and TemplateManagementPanel loading divs, the gradient renders behind visible text ("Loading BOM data…", "Loading templates…"). Typical skeleton patterns either use empty placeholder boxes or hide text during the shimmer. Text overlaid on a moving gradient may look unpolished. Consider using `color: transparent` on shimmer elements or removing the loading text.
