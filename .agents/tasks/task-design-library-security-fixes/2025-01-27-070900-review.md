# Server-side publication and selection hardening for Design Library

This change closes two critical trust-boundary gaps in the Design Library module. Previously, template publication was a direct client-side UPDATE on the `template` table (gated only by an RLS trigger), and Consultants could read metadata for non-ACTIVE templates via direct API. Now, publication is routed through an atomic `publish_template` RPC that validates DESIGNER ownership, DRAFT status, and full SKU/BOM eligibility before committing; `create_project` revalidates eligibility server-side after checking ACTIVE status; and three role-specific RLS policies replace the former blanket `USING(true)` SELECT grant.

Watch for: the frontend passes `userId` as `user?.id` (possibly `undefined`) to the RPC — if the auth store hasn't loaded yet, the call will hit the server with a null parameter rather than failing fast on the client (confirmed). The `publish_template` RPC and `create_project` both rely on the same `check_template_eligible` function, which does not check for dependency cycles or compatibility — the user's steering explicitly calls these out as P1 gaps not yet addressed.

**Verdict**: APPROVED

## High-level view

The publication boundary is now fully server-side. `publish_template` runs as SECURITY DEFINER, locks the template row with `FOR UPDATE`, validates every gate (auth, role, ownership, status, dependency eligibility), and only then flips status to ACTIVE. If any check fails the implicit transaction rolls back — no partial state is possible.

The selection boundary gains a second validation layer. `create_project` already required `status = 'ACTIVE'`, but a template could be ACTIVE while its underlying SKUs or catalogue entries degraded. The new `check_template_eligible` call after the status check ensures a direct RPC call cannot select a template whose dependencies have gone stale since publication.

Consultant visibility is tightened at the RLS level. The single `template_select_authenticated` policy (`USING(true)`) is replaced by three role-specific policies: CONSULTANT sees only ACTIVE, DESIGNER and ADMIN see all. An authenticated user whose role doesn't match any of the three sees nothing — fail-closed.

The frontend `publishStore.ts` now calls `supabase.rpc('publish_template')` instead of `fromTable('template').update()`. The store reads `userId` from the auth store but does not guard against it being undefined.

## Double-validation on the publish path

The existing `trg_template_activate` trigger on the `template` table calls `check_template_eligible` whenever status transitions to ACTIVE. Since `publish_template` already validates eligibility before issuing the UPDATE, the trigger re-runs the same six queries redundantly. This doubles the I/O cost of every successful publish. The trigger could be made conditional (skip when called from the definer context) or disabled within the function's transaction if publish volume grows.

## Undefined `userId` on the frontend call path

```typescript
const userId = useAuthStore.getState().user?.id;

const { data, error } = await supabase.rpc('publish_template', {
  p_template_id: templateId,
  p_user_id: userId,  // possibly undefined
});
```

If `user` is null (token expired, store not hydrated), `userId` is `undefined`. The Supabase client serializes this as `null`. On the server, the function compares `auth.uid()` against `p_user_id` — if both are null this passes the identity check, but `current_user_role()` would fail (no JWT means no `app_metadata`). The practical risk is a confusing error message rather than a security bypass, but a client-side guard (`if (!userId) { set error; return; }`) would prevent the round-trip entirely.

## RLS fail-closed for unknown roles

The three new policies form a closed set: CONSULTANT AND status='ACTIVE', DESIGNER (all), ADMIN (all). PostgreSQL RLS is deny-by-default — if no policy's USING clause evaluates to true, the row is invisible. A user with no role claim or an unexpected role value gets zero rows. This is worth noting because the previous single-policy design was fail-open for any authenticated user.

## Publication gates not yet covered by `check_template_eligible`

`check_template_eligible` validates six dependency chains (zone primary SKUs, zone alternatives, lighting, furniture, trim, hidden components) and requires an APPROVED master_bom. What it does **not** validate:

- **Compatibility validation** — no check that SKUs are mutually compatible or version-aligned
- **Dependency-cycle detection** — no check for circular references in template/component graphs
- **Availability flag** — the steering mentions `availability = AVAILABLE` but no such column exists in the current schema

These are acknowledged P1 future work per the user's steering, not regressions.

## Test coverage gaps

What is **not** tested: the undefined-userId path, the actual SQL behavior of `publish_template` (all tests mock the RPC), rejection scenarios (wrong role, non-owner, non-DRAFT status), and the new RLS policies. The E2E test failures in the task findings are pre-existing (missing `SUPABASE_URL` env var).
