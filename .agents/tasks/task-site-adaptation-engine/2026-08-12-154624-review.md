# Site Adaptation Engine — template geometry to site dimensions

A pure calculation engine that transforms zone widths and heights from a design template to match actual site measurements. Four width strategies (proportional scaling, priority-zone absorption, equal distribution, fixed passthrough) and three height modes, with per-zone min/max constraints and deterministic output ordering by zone_id. The engine follows the project's existing pattern of stateless engine functions that throw `EngineError` on invalid or impossible inputs.

Watch for: PROPORTIONAL strategy ignores `width_strategy: 'LOCKED'` — locked zones get scaled like everything else (confirmed). Height adaptation silently does nothing when only one of `template_wall_height` / `actual_wall_height` is supplied (confirmed). The sum-of-template-zone-widths is never validated against `template_wall_width`, so malformed input can produce silently wrong results (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

PROPORTIONAL unconditionally scales all zones regardless of their `width_strategy` field, meaning a zone marked `LOCKED` will still be resized — an inconsistency with EQUAL_DISTRIBUTION which honors the lock. The test suite never exercises PROPORTIONAL with a locked zone.

Height adaptation is keyed off a truthiness check on both wall-height fields. When only one is supplied, or when either is zero, the engine silently falls through to preserving original heights rather than throwing. A caller accidentally omitting one field gets no signal that height adaptation was skipped.

Constraint enforcement throws on any violation rather than clamping — fail-closed design. The engine never returns a partial result.

<details>
<summary>Issues (4)</summary>

1. **PROPORTIONAL ignores LOCKED zones** — Zones with `width_strategy: 'LOCKED'` are scaled proportionally, contradicting EQUAL_DISTRIBUTION's behavior. Either exclude locked zones from the ratio scaling (pinning them at original width and distributing the adjusted target among resizable zones) or document this as intentional spec behavior.
2. **Template-zone-sum vs template_wall_width not validated** — If the sum of zone widths doesn't equal `template_wall_width`, the proportional ratio is applied to each zone independently and the remainder distribution will silently produce a result that sums to `actual_wall_width` even though the zone proportions are now arbitrary. Add a validation check or document the tolerance.
3. **Height activation truthy check treats zero as absent** — `if (input.template_wall_height && input.actual_wall_height)` fails when either value is 0. The validation function doesn't reject zero heights — so a zero height silently disables height adaptation instead of throwing.
4. **No validation of zone_id uniqueness** — Duplicate zone_ids would cause the `Map` to silently overwrite earlier entries. The engine would return fewer output zones than input zones without error.

<summary>Details</summary>

## PROPORTIONAL strategy and the LOCKED gap

`applyProportional` receives the full zone array and scales every zone by `actual / template` regardless of `width_strategy`. Compare this to `applyEqualDistribution`, which explicitly filters out `LOCKED` zones and only distributes delta among resizable ones.

If the spec intends PROPORTIONAL to ignore locks (scale everything uniformly), that's a valid design choice but it creates a surprise for callers who expect `LOCKED` to mean "don't change this zone's width" across all strategies. If it should honor locks, the fix is: pin locked zones at their original width, subtract locked-width-total from both `template_wall_width` and `actual_wall_width`, then apply proportional scaling only to the resizable zones.

## Template-zone-sum coherence

Consider: `template_wall_width: 3000`, three zones of `[1000, 1000, 500]` (sum = 2500). The ratio becomes `actual / 3000`, applied to each zone's individual width. The remainder distribution forces the total to equal `actual_wall_width`, but the proportions are now distorted relative to what "proportional" should mean. A validation check like `Math.abs(sumOfZones - template_wall_width) > tolerance → EngineError` would catch template construction errors early.

## Height activation edge case

```typescript
if (input.template_wall_height && input.actual_wall_height) {
  // scale
} else {
  // preserve original heights
}
```

When `template_wall_height` is provided but `actual_wall_height` is not (or vice versa), the engine silently falls through to the preserve branch. The validation function doesn't enforce that they're either both present or both absent. A defensive option: if exactly one is provided, throw `EngineError` explaining that both are required for height adaptation.

## Zone_id uniqueness

The engine uses `zone_id` as a Map key throughout (adapted widths, adapted heights, output assembly). If two input zones share a zone_id, the second write overwrites the first silently. The output array would contain only the last zone's data for that id. Adding a uniqueness check in `validateInput` would be trivial and would prevent subtle bugs in upstream zone-construction code.

## Test coverage gaps

Not tested: PROPORTIONAL with `LOCKED` zones (the gap described above), inputs where zone-sum doesn't match `template_wall_width`, duplicate zone_ids, providing only one of the two wall-height fields, and negative `height_mm` values.
