# Multi-step project creation wizard with template snapshot freeze (v2)

All five issues from the v1 review are fixed: the hash uses a recursive `sortKeysDeep` replacer, customer/site references are embedded in `snapshot_data.project_metadata`, the idempotency key is persisted in state and reused on retry, the four template sub-queries run in parallel via `Promise.all`, and post-creation load failures are distinguished from creation failures (no Retry button when the project already exists).

Watch for: the snapshot hash is computed over `snapshotData` (without `project_metadata`) while the RPC receives `snapshotWithMetadata` (with `project_metadata`) — the hash doesn't cover the customer/site references that are part of the persisted payload (confirmed). The zone-SKU mapping silently drops all but the last SKU per zone if a zone has multiple bindings, since `Map.set` overwrites (likely — depends on schema cardinality).

**Verdict**: APPROVED

## High-level view

The hash/payload asymmetry is a design choice worth making explicit: `computeSnapshotHash(snapshotData)` hashes only the template-derived geometry and material data, while `snapshotWithMetadata` adds the mutable project metadata on top. If the backend uses the hash for integrity checking or deduplication, a change to customer/site references alone would not produce a different hash. The intent should be documented where the split happens.

The zone-SKU mapping iterates all `template_zone_sku` rows but stores results in a `Map<string, SkuMaster>` keyed by `zone_id`. If the join table allows multiple SKUs per zone (the `alternatives` field in `SnapshotZone` suggests it will), a second binding silently overwrites the first. The upstream `projectStore.ts` uses `upsert(..., { onConflict: 'zone_id' })`, suggesting a one-to-one constraint today — acceptable for now but will break silently when alternatives are introduced.

## Hash/payload split at project_metadata boundary

```typescript
const snapshotData = buildSnapshotData(/* ... */);

const snapshotWithMetadata = {
  ...snapshotData,
  project_metadata: {
    customer_reference: customerReference,
    site_reference: siteReference,
  },
};

const snapshotHash = await computeSnapshotHash(snapshotData);  // ← no metadata

await supabase.rpc('create_project', {
  p_snapshot_data: snapshotWithMetadata,  // ← has metadata
  p_snapshot_hash: snapshotHash,
});
```

If the server-side `create_project` function computes its own hash over the full `p_snapshot_data` JSONB for integrity or deduplication, the hashes will never match because the server-side input includes `project_metadata` but the client-side hash does not.

If this split is intentional — the hash is a content-addressable identifier for the design, not the full payload — a one-line comment at the `computeSnapshotHash` call site would prevent future confusion.

## Zone-SKU cardinality assumption

The snapshot builder declares `alternatives: unknown[]` but never populates it. The store's zone-SKU loading code uses `Map<string, SkuMaster>` — a structure that inherently stores one value per key:

```typescript
for (const zs of zoneSkuData as Array<{ zone_id: string; sku_id: string }>) {
  const sku = skuMap.get(zs.sku_id);
  if (sku) {
    zoneSku.set(zs.zone_id, sku);  // overwrites if zone_id repeats
  }
}
```

The upstream `projectStore.ts` enforces a unique constraint via `upsert({ zone_id, sku_id }, { onConflict: 'zone_id' })`, so the `template_zone_sku` table likely has a unique index on `zone_id` today. When multi-SKU per zone is introduced (to populate `alternatives`), this code will need to switch to `Map<string, SkuMaster[]>` and the snapshot builder will need to accept the array.
