# Multi-step project creation wizard with template snapshot freeze

A Zustand store drives a CONSULTANT-only wizard that walks through template browsing, detail entry, and atomic project creation via an RPC. The store fetches active templates from `perfecity.template`, assembles a frozen JSONB snapshot of the selected template's zones/lighting/furniture/trims (including zone-SKU bindings), hashes it with SHA-256, and calls `create_project` with an idempotency key. The UI is a fixed-position side panel with step-switching, error/retry, and auto-load of the new project on success.

Watch for: `customerReference` and `siteReference` are collected from the user but never transmitted to the backend (confirmed). The snapshot hash uses `JSON.stringify` with an array replacer that silently drops all nested object properties — the hash is computed over empty shells (confirmed). The idempotency key includes `Date.now()`, defeating deduplication on retry (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The creation store implements a state machine (IDLE → BROWSE_TEMPLATES → PROJECT_DETAILS → CREATING → CREATED/ERROR) with the multi-query snapshot assembly inside `createProject` as the most complex path — six sequential Supabase queries before calling the RPC.

The snapshot builder's hash function passes `Object.keys(snapshotData).sort()` as the replacer to `JSON.stringify`. When the replacer is an array, it acts as a property whitelist at *every* nesting level. Only top-level keys (`wall_geometry`, `zones`, `base_dimensions`, etc.) are in the array, so nested keys (`width_mm`, `height_mm`, `id`, `name`, `x_mm`, `sku_code`, …) are silently dropped. The hash is computed over `{"base_dimensions":{},"zones":[{}],...}` — an empty skeleton that does not represent the actual snapshot content.

The form collects `customerReference` and `siteReference` (both required, validated client-side) yet the RPC payload omits them entirely. User input is silently discarded.

The idempotency key is `${userId}-${templateId}-${Date.now()}` — every retry generates a new timestamp, so the key never deduplicates across retries of the same logical operation.

<summary>Issues (5)</summary>

1. **customerReference/siteReference not sent to backend** — The form requires both fields but `createProject` never passes them to `supabase.rpc`. Either include them in the RPC params or remove the form fields. (confirmed)
2. **Hash computed over empty skeleton** — `computeSnapshotHash` uses an array replacer that whitelists only top-level keys; all nested properties (zone dimensions, SKU data, lighting config) are dropped from the serialized string. The hash does not represent the snapshot. Replace the array with a recursive sort-keys replacer or use `json-stable-stringify`. (confirmed)
3. **Non-idempotent idempotency key** — `Date.now()` in the key means retries always produce a new key. Generate the key once when the user clicks "Create" and persist it in state across retries. (confirmed)
4. **Sequential queries without parallelism** — `createProject` awaits zone, lighting, furniture, and trim fetches sequentially. These are independent and could be `Promise.all`'d to cut round-trip latency. (confirmed)
5. **loadProject failure after successful RPC** — If `loadProject` throws after the RPC succeeds, the wizard transitions to ERROR with "Retry" available — but retrying would create a duplicate project. Distinguish post-creation failures from creation failures. (confirmed)

<summary>Details</summary>

## customerReference and siteReference dead-end

The store declares `customerReference` and `siteReference` as required state, the form enforces non-empty validation, and `setCustomerReference`/`setSiteReference` update the store. But `createProject` reads only `selectedTemplate` from state — it never references either field. The RPC parameters are `p_template_id`, `p_user_id`, `p_idempotency_key`, `p_snapshot_data`, `p_snapshot_hash`, `p_rule_set_id`. The `Project` type has `client_name` and `name` columns that appear to be the natural home for these values, but neither is populated. User input is silently discarded.

## Snapshot hash strips all nested data

```typescript
const canonical = JSON.stringify(snapshotData, Object.keys(snapshotData).sort());
```

When the second argument to `JSON.stringify` is an array, it acts as a property whitelist applied at **every** nesting level. The array here is `["base_dimensions", "calculation_parameters", "furniture", "hidden_components", "lighting", "trims", "wall_geometry", "zones"]`. Any key not in that list — `width_mm`, `height_mm`, `id`, `name`, `x_mm`, `sku_id`, `primary_sku`, etc. — is dropped from the output at all levels.

Verified result:
```
Input:  { base_dimensions: { width_mm: 3000, height_mm: 2700 }, zones: [{ id: "z1", name: "A" }], ... }
Output: {"base_dimensions":{},"zones":[{}],...}
```

The hash is computed over empty shells. Two snapshots with completely different zone configurations but the same top-level key structure will produce the same hash. The tests don't catch this because they use empty arrays for zones/lighting/furniture, and the "different hash" test changes `wall_geometry` (a top-level string that *is* preserved).

Fix: replace the array replacer with a function replacer that recursively sorts keys, or use a stable-stringify library.

## Idempotency key doesn't survive retries

```typescript
const idempotencyKey = `${userId}-${templateId}-${Date.now()}`;
```

Generated inside `createProject`, which runs on every attempt. If the backend uses this key to deduplicate (as the name implies), retries after transient failures will bypass the guard. The key should be generated once at the start of a creation attempt and stored in state so that retry reuses it.

## Sequential data loading

```
Current:  zone → lighting → furniture → trim → zone_sku → sku_master → RPC
Possible: [zone, lighting, furniture, trim] → [zone_sku, sku_master] → RPC
```

The first four queries are independent. `Promise.all` would cut ~3 round trips on slow connections.

## Post-creation failure conflation

After `supabase.rpc('create_project')` succeeds:

```typescript
await useProjectStore.getState().loadProject(projectId as string);
useCanvasStore.getState().setMode(CanvasMode.CONSULTANT);
```

Both are inside the same `try/catch` that transitions to `CreationStep.ERROR`. If `loadProject` throws (network blip, RLS timing), the wizard shows "Retry" → user clicks Retry → `handleRetry` resets to `BROWSE_TEMPLATES` → user could create a duplicate. The error path should distinguish post-creation from creation failures, offering "try loading again" instead of "start over."

## Test coverage gaps

The store tests mock `snapshotBuilder` entirely, so the hash truncation bug is invisible there. The snapshot builder tests use empty arrays/objects that happen to produce consistent (but meaningless) hashes. No test passes a snapshot with populated nested properties and verifies the hash includes that data.

Not tested: the `.in()` query path for zone-SKU mappings when multiple zones exist, and the post-RPC `loadProject` failure path.
