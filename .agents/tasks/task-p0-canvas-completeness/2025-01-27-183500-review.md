# Undo/Redo, keyboard shortcuts, consultant permissions, and alternative SKU selection

Four features land in a single branch: a zone-state history stack with undo/redo, keyboard shortcut handlers for zone manipulation, snapshot-driven permission enforcement for Consultant mode, and a panel for selecting promoted alternative SKUs. The implementation threads through the existing hook-per-interaction architecture — each feature is a new hook (`useHistory`, `useKeyboardShortcuts`, `usePermissionEnforcement`) plus minimal wiring in `CanvasContainer` and `Toolbar`. Zone mutations (drag, resize, create, delete, nudge) push state to history before applying, and the Consultant interactions gate on permission lookups from `snapshot_data`.

Watch for: The module-level singleton in useHistory leaks state across fast-refresh cycles and between test files that forget to call `resetHistory` (confirmed). The `canEditZone` permission check relies on a naming convention (`zone_{id}`) that has no type-level or runtime contract binding it to the snapshot schema (likely). Arrow nudge pushes a history entry on every keypress with no debounce, so holding an arrow key fills the 50-slot stack in under a second (confirmed).

**Verdict**: APPROVED

## High-level view

The history stack uses a module-level singleton (mutable `let stack` / `let cursor`) shared between `CanvasContainer` and `Toolbar` via a subscriber-notification pattern. This avoids prop-drilling but means the stack is never cleared when a user switches projects or templates within a session — stale zone arrays from a previous template remain undoable.

Keyboard shortcuts run as a second keydown listener layered atop the viewport's space-drag handler. The nudge path enforces `constrainToWall` and `hasOverlap` but pushes a history snapshot per arrow keypress with no coalescing, inflating the undo stack rapidly during held-key input.

Permission enforcement derives from `snapshot_data.permissions`, an untyped `Record<string, unknown>` cast to `SnapshotPermission[]`. Zone-level locking hinges on a `zone_{id}` key convention that nothing else in the codebase defines or validates — if the backend uses a different format, enforcement fails open.

The alternatives panel filters snapshot alternatives by zone ID and ACTIVE status, renders a button list, and calls the existing `assignSku` store action. No free-text SKU input exists, so arbitrary selection is structurally impossible.

## History singleton and subscriber lifecycle

The history module stores `stack` and `cursor` as `let` bindings at module scope. Components subscribe via a `Set<() => void>` and trigger re-renders through a `setTick` counter. The initial subscription happens inside a `useState` initializer (runs once per mount), but there is no corresponding cleanup:

```ts
// useHistory.ts — subscription without cleanup
useState(() => {
  subscribers.add(forceUpdate);
  return null;
});
```

If a component unmounts (navigating away from the canvas), its `forceUpdate` closure stays in the set. On remount, a new closure is added. The set grows unboundedly over a session with route changes. React 18+ suppresses the setState-on-unmounted warning but the memory leak remains.

The singleton is also never reset when the user loads a different project. Applying an undo from a previous template injects stale zone IDs into `projectStore.zones`.

## Arrow nudge and history inflation

```ts
// useKeyboardShortcuts.ts — every arrow keypress
history.pushState(zones);
void useProjectStore.getState().updateZone(updatedZone);
```

A 100ms key-repeat interval generates 10 history entries per second. With `MAX_HISTORY_SIZE = 50`, five seconds of held-arrow erases all prior meaningful states (creates, resizes, deletes) from the stack. A practical fix: coalesce consecutive nudge entries by replacing the top of the stack when the previous entry was also a nudge, or push only on keyup after a sequence.

## Permission enforcement fail-open posture

`canEditZone` returns `true` by default and only returns `false` when a permission with `parameter_key === 'zone_{id}'` and `edit_mode === 'LOCKED'` exists. This means:

- If the backend serializes the key differently (e.g. `zone.{id}`, or uses a zone name), the check silently passes.
- There is no RESTRICTED mode for zone-level interactions (only LOCKED), so partial constraints like "can resize but not move" are not expressible.
- If `snapshot_data.permissions` is missing entirely (malformed snapshot), the hook returns an empty array and all fields become editable — fail-open by design.

## MeasurementPanel dual-validation gap

`handleChange` applies a hard-coded range check:

```ts
if (field === 'wall_width_mm' && (numValue < 600 || numValue > 12000)) return;
```

The RESTRICTED permission's `min_value`/`max_value` (which may be tighter, e.g. 600–3000) is only checked in `handleBlur`. During typing, values between the permission max and 12000 are accepted into store state and autosaved. The error appears only after blur. This creates a window where an invalid value persists in the project and propagates via autosave.
