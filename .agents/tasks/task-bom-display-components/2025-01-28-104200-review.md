# BOM display panel — v2 review after fix pass

The four blocking issues from the v1 review have been addressed: `BomPanel` now contains a `useEffect` that triggers the appropriate fetch actions when the panel opens, `BomSectionTable` iterates all map keys (not just the hardcoded three) so unknown product types render, reconciliation uses `Math.abs(...) > 0.001` tolerance for quantity comparison, and the store carries per-tier loading flags (`isMasterBomLoading`, `isActualBomLoading`, `isFinalBomLoading`) whose OR-combination drives the aggregate `isLoading`. All 145 tests pass, TypeScript compiles cleanly.

Watch for: The `useEffect` dependency array includes object references (`currentTemplate`, `currentProject`) that will re-trigger fetches on every store update that replaces those objects (possible). The aggregate `isLoading` derivation is manually maintained in six locations — a stale `get()` call during concurrent fetches could briefly show wrong loading state (possible). The v1 concern about type safety loss in `BomSectionTable` (column key typos invisible at compile time) and absent RLS consideration remain unchanged but are non-blocking.

**Verdict**: APPROVED

## High-level view

The `useEffect` in `BomPanel` guards on `isBomPanelOpen`, branches on `isDesigner`, and calls the correct fetch actions with IDs from `projectStore`. Object-identity churn on `currentTemplate`/`currentProject` could cause redundant fetches if the project store reconstructs those objects on unrelated updates — depending on `currentTemplate?.id` instead of the full object would eliminate this.

The per-tier loading flags eliminate the race condition. Each fetch action sets its own flag on entry and clears it on exit, reading the other two flags via `get()` to derive the aggregate. The manual bookkeeping across six try/catch/no-data exit paths is the fragility surface — an early return that forgets to clear its flag would leave the panel in a permanent loading state.

`BomSectionTable` now builds a `renderOrder` array that starts with the three known types, then appends any additional keys discovered in the data. Unknown product types appear at the bottom under their raw enum value as the section header.

## useEffect wiring — the fix for "button never fetches"

The fix adds a `useEffect` in `BomPanel`:

```tsx
useEffect(() => {
  if (!isBomPanelOpen) return;

  if (isDesigner && currentTemplate) {
    fetchMasterBom(currentTemplate.id);
  } else if (!isDesigner && currentProject) {
    fetchActualBom(currentProject.id);
    fetchFinalBom(currentProject.id);
  }
}, [isBomPanelOpen, isDesigner, currentTemplate, currentProject, fetchMasterBom, fetchActualBom, fetchFinalBom]);
```

The panel fetches on open and re-fetches if the user switches mode or loads a different template/project while the panel remains open. The dependency on `fetchMasterBom` etc. is stable (Zustand action references don't change), so those don't cause spurious re-runs.

The concern is `currentTemplate` and `currentProject` as object references. If `useProjectStore` reconstructs these objects without changing their `id` (e.g., spreading a new state that includes the same template data), React sees a new reference and the effect fires again, issuing redundant Supabase queries. Not a correctness bug — just unnecessary network traffic. The idiomatic fix:

```tsx
const templateId = useProjectStore((s) => s.currentTemplate?.id);
const projectId = useProjectStore((s) => s.currentProject?.id);
```

Then depend on `templateId` / `projectId` in the effect.

## Per-tier loading flags — the fix for concurrent fetch race

Each fetch action sets its own flag, then on every exit path reads the other two via `get()`:

```ts
const { isActualBomLoading, isFinalBomLoading } = get();
set({
  isMasterBomLoading: false,
  isLoading: isActualBomLoading || isFinalBomLoading,
});
```

The derivation is repeated in six places (success/error/no-data × 3 tiers). A missed update in any branch would leave `isLoading` stuck permanently. A derived approach — either a Zustand `subscribeWithSelector` that computes `isLoading` reactively, or centralizing the flag-clearing in a shared `finally` block — would reduce the maintenance surface from six sites to one.
