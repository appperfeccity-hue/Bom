# BOM display panel with Master/Actual/Final tables and reconciliation

This change adds a complete Bill of Materials viewing layer: TypeScript interfaces modeling six BOM-related database tables, a Zustand store (`bomStore`) that fetches and compares BOM data via Supabase, and a set of React components (`BomPanel`, `MasterBomTable`, `ActualBomTable`, `FinalBomTable`, `BomReconciliationView`, `BomSectionTable`, `BomStatusBadge`) that render the data in a mode-dependent overlay panel. The panel shows Master BOM + reconciliation in Designer mode, and Actual + Final BOM in Consultant mode. 37 new tests cover the store logic and component rendering.

Watch for: The BOM button opens the panel but never triggers data fetching — it only calls `openBomPanel()` without invoking any `fetch*` action, so the panel will always render in its empty state unless the caller manually populates the store (confirmed). The `BomSectionTable` drops lines whose `product_type` doesn't match the three hardcoded values, silently losing data (confirmed). Reconciliation comparison uses float equality for quantity, which will produce false positives with calculated waste/rounding (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The store follows the established `skuStore` pattern — Zustand slice with `isLoading` / `error` gating, `fromTable` queries, and a panel-open boolean. Each BOM tier (master, actual, final) gets its own fetch action that queries the parent record, then its line-items. The reconciliation engine is a synchronous in-memory diff driven by `master_bom_line_id` linkage, classifying each pair into one of six result types.

The component tree is a straightforward overlay: `BomPanel` owns the chrome and mode-branching, delegates to `MasterBomTable`/`ActualBomTable`/`FinalBomTable` for data display, and those delegate to a shared `BomSectionTable` that groups lines by `product_type` and renders per-section totals. The grouping component uses `Record<string, unknown>[]` as its line type, trading type safety for reuse across three different line shapes.

The wiring gap is the critical issue: `App.tsx` binds the BOM button to `openBomPanel()` alone, with no `fetchMasterBom` / `fetchActualBom` / `fetchFinalBom` call. The panel opens, finds null BOMs, and shows the empty-state messages. This is the only blocking concern.

<details>
<summary>Issues (5)</summary>

1. **BOM button never fetches data** — `openBomPanel()` in `App.tsx` does not call any fetch action. Wire it to `fetchMasterBom(templateId)` or `fetchActualBom(projectId)` / `fetchFinalBom(projectId)` depending on mode, or trigger fetches inside `BomPanel` on mount.
2. **BomSectionTable silently drops unknown product types** — Lines with a `product_type` not in `[WALL_PANEL, LIGHT, FURNITURE]` are grouped into a map entry that is never iterated (only `sectionOrder` drives rendering). Add a catch-all "Other" section or render all keys from the map.
3. **Float equality in reconciliation quantity comparison** — `actualLine.quantity !== masterLine.default_quantity` uses strict equality on numbers that may have fractional precision from calculation rules. Consider a tolerance or rounding strategy.
4. **Concurrent fetch race on shared `isLoading`** — All three fetch actions write to the same `isLoading` boolean. If `fetchActualBom` and `fetchFinalBom` are called in parallel (likely for Consultant mode), the first to resolve sets `isLoading: false` while the other is still in-flight, hiding the loading indicator prematurely.
5. **No RLS/auth consideration for BOM queries** — The store queries `master_bom`, `actual_bom`, and `final_bom` without row-level security context beyond the project/template ID filter. If RLS policies aren't in place on these tables, any authenticated user can read any project's BOM data.

## Data fetch wiring gap in App.tsx

The BOM button handler in `App.tsx` only calls `openBomPanel()`:

```tsx
<button onClick={openBomPanel} data-testid="bom-open-btn">BOM</button>
```

None of the three fetch actions (`fetchMasterBom`, `fetchActualBom`, `fetchFinalBom`) are invoked anywhere in the diff. The panel's content area branches on `isLoading` and `error`, then renders the table components — but since no fetch ever fires, the store retains its initial null state and each table renders its "No X BOM found" fallback. This makes the entire feature non-functional from the user's perspective.

The fix requires either calling the appropriate fetch in the button handler (needs a `templateId` or `projectId` from somewhere — currently not available in `App.tsx`) or adding a `useEffect` inside `BomPanel` that triggers fetches based on the current mode and some project/template context.

## BomSectionTable product-type filtering

`BomSectionTable` pre-seeds a `Map` with three keys (`WALL_PANEL`, `LIGHT`, `FURNITURE`), then iterates only those keys via `sectionOrder`. Lines whose `product_type` is something else (or a future enum member) get added to the map under their own key, but that key is never rendered because only `sectionOrder` drives the `map()` call. This is a silent data-loss path — no error, no warning, the line just vanishes from the UI.

## Reconciliation: float equality and SKU-precedence ordering

The reconciliation logic checks SKU change before quantity change:

```ts
} else if (actualLine.sku_id !== masterLine.sku_id) {
  // SKU_CHANGED
} else if (actualLine.quantity !== masterLine.default_quantity) {
  // QUANTITY_CHANGED
```

The ordering is semantically sound (if the SKU changed, quantity comparison is meaningless). However, the quantity comparison uses JavaScript `!==` on numbers. If `default_quantity` is `5` and the actual calculation produces `5.0000000001` due to floating-point arithmetic in the BOM engine, the line will be classified as QUANTITY_CHANGED when it is semantically unchanged. Whether this matters depends on how the backend engine stores results, but the frontend has no tolerance buffer.

## Concurrent isLoading race

In Consultant mode, the intended flow calls both `fetchActualBom` and `fetchFinalBom`. Both set `isLoading: true` at entry and `isLoading: false` at exit. If called in parallel:

```
fetchActualBom starts → isLoading: true
fetchFinalBom starts → isLoading: true (no-op, already true)
fetchActualBom resolves → isLoading: false ← premature
fetchFinalBom still in flight but UI shows content
```

The UI may flash partial content while the second fetch is still pending. Separate loading flags per BOM tier, or a reference-counted approach, would avoid this.

## Type safety erosion in BomSectionTable

All three table components cast their typed line arrays through `as unknown as Record<string, unknown>[]` to satisfy `BomSectionTable`'s generic prop type. This works at runtime but means the component cannot statically verify that `columns[n].key` actually exists on the line objects. A typo in a column key (e.g., `'sku_id'` vs `'sku_code'`) renders empty cells with no compile-time warning. A generic `<T extends Record<string, unknown>>` parameterization on the component would preserve the caller's type while still allowing generic rendering.

## Test coverage and gaps

The 37 new tests cover: store initial state, open/close, reset, all three fetch actions (happy path and error), all six reconciliation result types including a mixed-scenario test, component rendering in both modes, section grouping, totals rows, status badge colors, reconciliation view rendering, and immutability badge.

Not tested: the actual data flow from button click to fetch (because it doesn't exist yet), error states specific to the second query in a two-query fetch (e.g., master_bom succeeds but master_bom_line fails), behavior when `product_type` values fall outside the three known types, and the race condition with concurrent fetches.
