# CAD-style panel redesign for WallConfigPanel and ZonePropertiesPanel

Both configuration panels get a visual overhaul: hard-coded hex colors replaced with design-system CSS custom properties, sections separated with dividers and uppercase headers, form inputs standardized to 32px height with inline "mm" unit suffixes, and lighting/furniture forms switched to progressive disclosure (hidden until "+ Add" is clicked). New L-Corner segment width fields are conditionally rendered in WallConfigPanel. No store logic, callbacks, or validation functions changed.

Watch for: the progressive disclosure pattern is a **behavioral** change — form fields are no longer present in the DOM until the user clicks a button, which shifts test interaction flow (confirmed). Duplicate `data-testid="add-light-btn"` and `data-testid="add-furniture-btn"` appear in two DOM locations each, which will cause `getByTestId` to throw if both instances render simultaneously (likely — mutually exclusive render paths prevent this in practice, but the contract is fragile).

**Verdict**: APPROVED

## High-level view

Progressive disclosure replaces always-visible forms for Lighting and Furniture. A `showAddForm` boolean per section gates rendering; the form auto-closes on successful insert. Because the two `data-testid="add-light-btn"` elements are in mutually exclusive render branches (`!showAddForm` vs `showAddForm`), only one is in the DOM at a time — but future refactors that change this gating could break test selectors silently.

The new L-Corner segment fields (`segment_a_width_mm`, `segment_b_width_mm`) are an additive UI feature that surfaces existing config keys the engine already consumes. No new data-testid attributes were added for these fields, leaving them untestable via selector queries.

The style constants use `var()` references throughout. Three `rgba()` values remain for alpha-channel tints the design system doesn't tokenize; one bare `#FFFFFF` in ZonePropertiesPanel's `BUTTON_PRIMARY_STYLE` could be `var(--color-surface)` for consistency.

Both root `<div>` elements apply `className="... panel"` alongside inline styles that override the same CSS properties the `.panel` class sets — making the class partially dead code while the inline styles are the actual source of truth.

## Progressive disclosure in Lighting and Furniture sections

The original component rendered all form fields unconditionally. The new version wraps them in `{showAddForm && (...)}`, initializing to `false`. On successful add:

```tsx
if (!error) {
  await loadTemplate(currentTemplate.template_id);
  setShowAddForm(false);
}
```

The select/input elements (`select-edge-selection`, `select-lighting-mounting-type`, `input-position-x`, `input-position-y`, `select-orientation`) are absent from the DOM until the user clicks "+ Add". No existing unit tests query these IDs directly (verified via grep), so all 1144 tests pass. Future component-level tests will need to simulate the add-button click before asserting on form content.

The duplicate testid situation:

```
Header button:  data-testid="add-light-btn"    (rendered when !showAddForm)
Submit button:  data-testid="add-light-btn"    (rendered when showAddForm)
```

React Testing Library's `getByTestId` throws on multiple matches. Only one is ever mounted today, but the semantic contract is violated at the declaration level. Renaming the submit instance to `submit-light-btn` / `submit-furniture-btn` would harden this.

## L-Corner segment fields — missing test selectors

The new fields call `handleNumberChange('segment_a_width_mm', ...)` and `handleNumberChange('segment_b_width_mm', ...)` through the existing generic dispatcher. No `data-testid` attributes were added for these inputs, making them unreachable via standard test selectors. If component-level tests are added for L-Corner configuration later, they'll need either testids or label-based queries.

## Inline style / CSS class overlap

WallConfigPanel's root div applies `className="wall-config-panel panel"` alongside inline `backgroundColor`, `borderLeft`, `padding`, and `width`. The `.panel` class in `components.css` sets identical properties. Inline styles win by specificity, so the class values are overridden. If someone modifies the `.panel` class expecting it to change this panel's appearance, nothing will happen. The same pattern exists in ZonePropertiesPanel.
