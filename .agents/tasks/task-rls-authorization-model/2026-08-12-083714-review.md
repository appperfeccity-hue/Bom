# RLS authorization model for the PERFECCITY schema (v2)

This migration enables Row Level Security on all 34 tables in the `perfecity` schema and creates ~151 policies implementing a four-role authority model (ADMIN, DESIGNER, CONSULTANT, SYSTEM). A corrective commit addressed the seven issues from the v1 review: `anon` USAGE revoked, snapshot UPDATE policy removed, Master BOM DESIGNER UPDATE scoped to template ownership, DESIGNER SELECT added for final_bom/final_bom_line, and audit INSERT policy removed. Watch for: the scoping inconsistency between `actual_bom` DESIGNER SELECT (unscoped — all projects visible) and `final_bom` DESIGNER SELECT (scoped to own templates) (confirmed), and the absence of behavioral RLS tests that verify actual policy enforcement (confirmed, acknowledged as infeasible via MCP).

**Verdict**: APPROVED

## High-level view

The grant strategy now correctly excludes `anon` and grants schema access only to `authenticated`. The `FORCE ROW LEVEL SECURITY` omission is documented with clear reasoning for the Supabase architecture.

One scoping asymmetry remains in the DESIGNER SELECT layer: `actual_bom`/`actual_bom_line` are unscoped (any designer sees all projects' BOMs), while `final_bom`/`final_bom_line` DESIGNER SELECT is scoped to own-template projects. This is a data-leakage concern of low severity — actual BOMs contain quantity details for other designers' templates — but the inconsistency means the policy set expresses two contradictory intent models simultaneously.

The test harness validates all seven corrective items structurally (policy existence/absence, USING clause content patterns) but does not exercise actual authorization enforcement. Behavioral tests remain the most important gap for production readiness.

## Actual BOM DESIGNER SELECT scoping asymmetry

The corrective commit added ownership-scoped DESIGNER SELECT on `final_bom` and `final_bom_line`:

```sql
CREATE POLICY final_bom_select_designer ON perfecity.final_bom
  FOR SELECT TO authenticated
  USING (
    perfecity.current_user_role() = 'DESIGNER'
    AND EXISTS (
      SELECT 1 FROM perfecity.project p
      JOIN perfecity.template t ON t.template_id = p.template_id
      WHERE p.project_id = final_bom.project_id
        AND t.created_by = auth.uid()
    )
  );
```

But `actual_bom` and `actual_bom_line` remain unscoped:

```sql
CREATE POLICY actual_bom_select_designer ON perfecity.actual_bom
  FOR SELECT TO authenticated
  USING (perfecity.current_user_role() = 'DESIGNER');

CREATE POLICY actual_bom_line_select_designer ON perfecity.actual_bom_line
  FOR SELECT TO authenticated
  USING (perfecity.current_user_role() = 'DESIGNER');
```

The spec (section 8, DESIGNER permissions) says "View Projects using own Templates: YES" — not "view all projects." The `project_select_designer` policy is also unscoped (`USING (perfecity.current_user_role() = 'DESIGNER')`), which creates a consistent pattern of designers seeing all projects. If the intent is "designers see all projects" then `final_bom_select_designer` is over-scoped. If the intent is "designers see only projects using their templates" then `project_select_designer`, `actual_bom_select_designer`, and `actual_bom_line_select_designer` are under-scoped. The current state is internally inconsistent.
