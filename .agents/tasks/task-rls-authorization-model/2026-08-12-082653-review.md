# RLS authorization model for the PERFECCITY schema

This migration enables Row Level Security on all 34 tables in the `perfecity` schema and creates 151 policies implementing a four-role authority model (ADMIN, DESIGNER, CONSULTANT, SYSTEM). The approach uses a single JWT-extraction helper function (`perfecity.current_user_role()`) as the policy decision point, with ownership checks (`created_by = auth.uid()`) gating write access to template and project hierarchies. Watch for: the `anon` grant that opens schema access to unauthenticated users (confirmed), the `project_snapshot` UPDATE policy that conflicts with the immutability invariant (confirmed), the `master_bom` DESIGNER UPDATE policy that lacks ownership scoping (confirmed), and missing DESIGNER SELECT policy on `final_bom`/`final_bom_line` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The grant strategy opens the schema to both `authenticated` and `anon` roles. The `anon` USAGE grant means any unauthenticated Supabase client can access the schema, and without explicit deny-all policies for `anon`, the default-deny of RLS is the only barrier. A single future permissive `anon` policy on any table would expose the entire schema to the public internet.

The trust boundary sits entirely at the Supabase auth layer — anyone who can craft a JWT with `app_metadata.role = 'ADMIN'` owns the database. Acceptable for the MVP, but worth documenting explicitly.

The `master_bom` and `master_bom_line` UPDATE policies for DESIGNER are not scoped to ownership — any designer can approve any other designer's Master BOM, violating the spec's "Modify other Designer's Template: NO" rule.

`project_snapshot` has a CONSULTANT UPDATE policy, but the baseline DDL has a trigger (`trg_snapshot_immutable`) that prevents all UPDATEs. This creates a "policy says yes, trigger says no" layering where an attacker probing for authorization errors gets a trigger exception instead of a clean RLS denial. If the trigger is ever dropped, the RLS layer becomes the last defense — and it permits the mutation.

The `final_bom` and `final_bom_line` tables have no DESIGNER SELECT policy despite the spec allowing Designers to view projects using their own templates. This is an asymmetry with `actual_bom`/`actual_bom_line` which do have DESIGNER SELECT.

The audit event table allows any authenticated user to INSERT arbitrary records. Since audit writes should be atomic with system mutations (all performed by service_role), this opens the trail to pollution from client-side code.

The test harness validates only structural properties (counts, existence) without testing any actual authorization enforcement.

<summary>Issues (7)</summary>

1. **`anon` role granted USAGE on perfecity schema** — Remove the `anon` grant from `GRANT USAGE ON SCHEMA perfecity TO authenticated, anon`. Unauthenticated clients should not reach the schema at all.
2. **`project_snapshot` UPDATE policy contradicts immutability trigger** — Remove the `project_snapshot_update_consultant` policy. The snapshot is immutable by design; granting RLS UPDATE creates a defense-in-depth gap if the trigger is ever dropped.
3. **`master_bom` / `master_bom_line` DESIGNER UPDATE not ownership-scoped** — Add an ownership filter: the DESIGNER UPDATE policy on `master_bom` should verify the parent template's `created_by = auth.uid()`. Same for `master_bom_line`.
4. **Missing DESIGNER SELECT on `final_bom` and `final_bom_line`** — Add DESIGNER SELECT policies mirroring the actual_bom pattern. The spec says Designers can view projects using their own templates.
5. **No behavioral RLS tests** — Add tests that SET ROLE and verify actual policy enforcement: Consultant A cannot see Consultant B's project, Designer cannot INSERT into `sku_master`, etc.
6. **Audit event INSERT open to all authenticated** — Remove the `audit_event_insert_authenticated` policy. Audit writes should be restricted to service_role only (which already bypasses RLS), preventing user-crafted audit trail pollution.
7. **No `FORCE ROW LEVEL SECURITY` and blanket SELECT grant** — If RLS is accidentally disabled on any table, the blanket `GRANT SELECT ON ALL TABLES` means all data is exposed. Consider adding `FORCE ROW LEVEL SECURITY` or document why it's unnecessary in Supabase.

## `anon` schema USAGE opens an unnecessary attack surface

Line 24 of the migration:

```sql
GRANT USAGE ON SCHEMA perfecity TO authenticated, anon;
```

The `anon` role is Supabase's unauthenticated client role. Granting it USAGE means any public API key holder can attempt to query `perfecity.*` tables. RLS's default-deny protects today (no policies target `anon`), but this is a fail-open posture: a single future `TO public` or `TO anon` policy on any table exposes data to the internet. The `anon` grant provides zero value — no policy in this migration references `anon`, and the specification explicitly requires authentication for all access. Remove it.

## Snapshot UPDATE policy contradicts architectural immutability

The spec (sections 69-72) declares project snapshots immutable. The baseline DDL enforces this with `trg_snapshot_immutable`. Yet the RLS migration creates:

```sql
CREATE POLICY project_snapshot_update_consultant ON perfecity.project_snapshot
  FOR UPDATE TO authenticated
  USING (
    perfecity.current_user_role() = 'CONSULTANT'
    AND EXISTS (...)
  );
```

If the trigger is accidentally dropped, the RLS layer permits snapshot mutation by the owning Consultant. A Consultant attempting an UPDATE today gets an opaque trigger error instead of a silent RLS denial. Removing the policy makes RLS reflect the true contract: no one can UPDATE snapshots through the authenticated role.

## Master BOM DESIGNER UPDATE lacks ownership scope

```sql
CREATE POLICY master_bom_update_designer ON perfecity.master_bom
  FOR UPDATE TO authenticated
  USING (perfecity.current_user_role() = 'DESIGNER');
```

Any DESIGNER can update any Master BOM — approve it, invalidate it — regardless of template ownership. The spec (section 64) restricts approval to the template's own designer. The fix:

```sql
USING (
  perfecity.current_user_role() = 'DESIGNER'
  AND EXISTS (
    SELECT 1 FROM perfecity.template t
    WHERE t.template_id = master_bom.template_id
      AND t.created_by = auth.uid()
  )
)
```

The same gap applies to `master_bom_line_update_designer` which should join through `master_bom` to `template`.

## DESIGNER cannot SELECT final_bom / final_bom_line

The `actual_bom` and `actual_bom_line` tables include a DESIGNER SELECT policy, but `final_bom` and `final_bom_line` do not. A designer can see the in-progress BOM but not the finalized result for projects using their templates — an inconsistency with the spec's "View Projects using own Templates: YES."

## Audit event INSERT is too permissive

```sql
CREATE POLICY audit_event_insert_authenticated ON perfecity.audit_event
  FOR INSERT TO authenticated
  WITH CHECK (true);
```

Any authenticated user can insert arbitrary audit records with any `actor_id`, `event_type`, and `entity_id`. The specification says audit events are "committed atomically with state mutation" — written by system functions running as `service_role`. A malicious client can flood the audit trail with fabricated events. Remove the policy; `service_role` already bypasses RLS.

## Test harness validates structure, not authorization

The five tests check metadata (table count, policy count, function existence, schema privilege). Critical scenarios untested:

- Consultant A cannot SELECT Consultant B's project
- DESIGNER cannot INSERT into `sku_master`
- CONSULTANT cannot UPDATE `template`
- DESIGNER can only UPDATE their own template's Master BOM
- `anon` role cannot SELECT from any table

A regression that silently drops a critical policy would pass the current harness.
