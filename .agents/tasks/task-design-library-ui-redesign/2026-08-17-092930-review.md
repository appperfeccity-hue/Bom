# Design Library UI redesign to premium image-first gallery

The Design Library has been transformed from a dropdown-filtered grid grouped by design family into a vertically-stacked gallery composed of a category carousel (room types), circular look swatches (design families), a chip-based filter bar, and an image-first template card grid. The store (`designLibraryStore.ts`) is intentionally untouched; a local `useState` in the parent component layers a `wall_application` category filter on top of the store's existing filter pipeline. The previous `<select>` elements for geometry and availability have been removed entirely from the UI — their values can only be *cleared* via chips but can no longer be *set* by the user.

Watch for:
- **Geometry and availability filters are now unreachable** (confirmed) — users cannot set `wallGeometry` or `availability` filters because the dropdowns were removed and no replacement UI sets them.
- **Favorite heart state is ephemeral** (confirmed) — `isFavorited` lives in component-local `useState`, resets on every re-render/unmount, and is not persisted or surfaced to the parent.
- **No unit tests for the three new components** (confirmed) — `CategoryCarousel`, `LookSwatches`, and `FilterChipBar` have zero test coverage.

**Verdict**: NEEDS_CHANGES

## High-level view

The composition layer in `DesignLibrary.tsx` replaces the old family-grouped grid with a vertical stack: search bar, category carousel, look swatches, filter chip bar, flat template grid, and the preview panel. The store remains the single source of truth for fetching and filtering; the only addition is a local `activeCategory` state that post-filters `filteredTemplates` by `wall_application` before display. This avoids store modification but creates an asymmetry: the category filter is invisible to the store, so it won't appear in any future URL-sync or persistence.

The `EnhancedTemplateCard` shifts from a data-dense layout to a tall image placeholder with a heart button, an availability dot (replacing the text badge), and bottom-aligned metadata. Test compatibility is maintained via a visually-hidden `<span>` inside the dot that carries the `AVAILABLE`/`BLOCKED` text for `textContent` assertions.

Filter discoverability is the biggest functional regression. The old UI had `<select>` elements for geometry (`STRAIGHT`, `L_CORNER`) and availability (`ALL`, `AVAILABLE`, `BLOCKED`). Those are gone. The `FilterChipBar` can *display and clear* these filters, but nothing in the new UI *sets* them. Any template attribute only reachable via geometry or availability is now inaccessible to users unless an external component pushes those filter values into the store.

1. **Geometry and availability filters unreachable** — The `<select>` dropdowns for wall geometry and availability were removed with no replacement affordance. Re-add a filter mechanism (dropdown, popover, or chip-creation UI) so users can activate these filters, not just clear them.
2. **Ephemeral favorite state** — The heart toggle in `EnhancedTemplateCard` uses component-local `useState` that resets on unmount and is invisible to parent/store. Either lift state into the store (or a dedicated favorites store) or remove the heart UI until persistence is ready.

4. **Category filter invisible to store** — The `activeCategory` filter lives outside the Zustand store, so it won't participate in any future URL-sync, deep-linking, or state-persistence mechanisms. Consider documenting this as intentional tech debt or migrating it to a UI-state slice.

<summary>Details</summary>

## Unreachable geometry and availability filters

The old `DesignLibrary` rendered three `<select>` elements: design family, wall geometry, and availability. The redesign replaces the design-family dropdown with the `LookSwatches` component (which calls `setDesignFamilyFilter`), but geometry and availability have no replacement setter. The `FilterChipBar` receives clear callbacks and "Clear all" resets them:

```tsx
const handleClearAll = () => {
  setActiveCategory(null);
  setSearchFilter('');
  setDesignFamilyFilter(null);
  setWallGeometryFilter(null);   // can clear...
  setAvailabilityFilter('ALL');  // can clear...
};
```

…but nowhere in the new component tree is `setWallGeometryFilter('L_CORNER')` or `setAvailabilityFilter('AVAILABLE')` ever called. A user interacting solely with this gallery cannot filter by geometry or availability. This is a functional regression from the prior UI.

## Ephemeral favorite state in EnhancedTemplateCard

Each card tracks `isFavorited` via `useState(false)`. This state resets when the card unmounts (e.g., filtered out and back), is not communicated to the parent via props or callbacks, and is not stored in any Zustand slice or backend. A user favorites a template, applies a filter, clears it, and the heart is gone. The toggle creates interaction affordance with no durable effect — it should either be backed by a store or hidden until persistence is ready.

## Category filter resets on remount

The `activeCategory` state lives in `DesignLibrary` as local `useState`. The `CategoryCarousel` correctly derives categories from the full `templates[]` array (not `filteredTemplates`) so categories remain visible even when other store-level filters reduce the result set. However, because it's local component state, the category selection resets on any remount of `DesignLibrary` (e.g., route change and return). The FEAT-001 findings acknowledge this as intentional to preserve the store constraint.

## Scroll containers lack scrollable-region semantics

The carousel and swatches scroll containers (`dl-category-carousel__scroll`, `dl-look-swatches__scroll`) don't expose `role="region"` or `aria-label` to indicate the scrollable area. Individual items are keyboard-reachable via `tabIndex={0}`, but assistive technology won't announce the container as scrollable. Minor and non-blocking.

## Test coverage gap for new filter components

`CategoryCarousel`, `LookSwatches`, and `FilterChipBar` have no dedicated test files. The filter interaction paths — clicking a category, clicking a swatch, removing a chip, clearing all — are not exercised by any integration test that renders `DesignLibrary` with a mocked store. The existing 1205 tests pass because they test the card and preview panel in isolation, but the new composition and filter behavior is uncovered.
