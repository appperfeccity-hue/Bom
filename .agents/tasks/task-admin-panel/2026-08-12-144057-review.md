# Full ADMIN panel with CRUD pages and Zustand store

This change introduces a complete admin panel — route guard, sidebar layout, a monolithic Zustand store managing six domain entities, and six CRUD page components covering families, design families, SKUs, compatibility rules, catalogue entries, and rule sets. The approach puts all admin data logic in a single flat store (`adminStore.ts`, ~500 lines) and all authorization in a lightweight route-level guard that checks `role === 'ADMIN'`. File uploads go to Supabase Storage with timestamp-based paths. Watch for: shared `isLoading` flag creates race conditions across concurrent fetches (confirmed); catalogue approval has no asset-presence guard (confirmed); delete operations lack confirmation UX and cascade awareness (confirmed); rule-set status transitions are unconstrained (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The admin store is a single Zustand slice with ~30 async actions and one `isLoading` boolean shared across all of them. Any concurrent fetch — and the pages fire multiple on mount — means an early-returning action can flip `isLoading: false` while a later one is still in flight, producing phantom "loading done" states and hiding errors from the previous call.

SKU creation validates product-type-dependent dimensions and gh/gv range client-side, which is the right place for immediate feedback, but the catalogue "Approve Ready" action blindly transitions status to READY without verifying that the required assets (GEOMETRY, PATTERN, RENDER) actually exist for the entry. An admin could mark an incomplete entry as ready.

Rule-set status transitions allow any transition (`transitionRuleSetStatus` takes an arbitrary string), though the UI only exposes DRAFT→ACTIVE→SUPERSEDED. The store itself doesn't enforce the state machine, so any caller of the action could skip states or go backwards.

Delete operations on families, categories, and design families fire immediately with no confirmation step and no awareness of FK constraints — a family with child categories or SKUs will produce an unhandled Supabase error that surfaces as a generic red banner.

The route guard (`AdminRoute`) is purely client-side and relies on the auth store's `role` field. It assumes Supabase RLS on the backend enforces the same constraints server-side; if RLS is missing or misconfigured, non-admin users could call the same `fromTable()` queries directly.

1. **Shared isLoading race** — The single `isLoading` boolean is set/cleared by every async action. Pages that call multiple fetches on mount (e.g., SkuMasterPage calls `fetchSkus`, `fetchFamilies`, `fetchCategories`) will see incorrect loading states. Split into per-domain or per-action loading flags.
2. **Catalogue approve without asset check** — `approveCatalogueEntry` sets status to READY without verifying required assets exist. Add a pre-check that queries `catalogue_asset` for the entry and blocks if any required type is missing.
3. **Unconstrained rule-set transitions** — `transitionRuleSetStatus` accepts any string. Enforce the DRAFT→ACTIVE→SUPERSEDED state machine in the store action or reject invalid transitions.
4. **No delete confirmation** — Family, category, design family, and design subfamily deletes fire immediately on click. Add a confirmation dialog or undo mechanism.
5. **FK cascade blindness** — Deleting a family that has child categories or SKUs will fail at the database level with an opaque error. Surface a human-readable message or pre-check children before attempting delete.
6. **Upload path predictability** — Catalogue asset paths use `${skuId}/${assetType}/${Date.now()}.${ext}`, which is guessable. If the storage bucket lacks per-user RLS, any authenticated user could overwrite assets. Consider adding a random suffix or UUID.
7. **Empty content_hash on upload** — The asset record is inserted with `content_hash: ''`. If downstream logic relies on content_hash for deduplication or integrity checks, this will silently break.

## Single-store loading flag race

Every async action in `adminStore.ts` follows the pattern `set({ isLoading: true, error: null })` at the top and `set({ ..., isLoading: false })` at the bottom. When SkuMasterPage mounts, it calls `fetchSkus()`, `fetchFamilies()`, and `fetchCategories()` in a single `useEffect`. If `fetchFamilies` resolves first it sets `isLoading: false` while `fetchSkus` is still in-flight; the UI drops its loading indicator prematurely. The same problem exists in CataloguePage (which calls `fetchCatalogueEntries` then `fetchCatalogueAssets` on selection) and SkuCompatibilityPage (`fetchCompatibilityRules` + `fetchSkus`).

The `error` field has the same issue — the last action to resolve wins, potentially overwriting an earlier failure's error message.

A straightforward fix is per-entity loading flags (`isLoadingSkus`, `isLoadingFamilies`, etc.) or a loading-count/semaphore pattern.

## Catalogue approval without asset-presence guard

In `adminStore.ts`, `approveCatalogueEntry` directly updates `catalogue_entry.status = 'READY'`:

```ts
approveCatalogueEntry: async (entryId: string) => {
  const { error } = await fromTable('catalogue_entry')
    .update({ status: 'READY' })
    .eq('catalogue_entry_id', entryId);
}
```

The feature spec says entries should have GEOMETRY, PATTERN, and RENDER assets before being marked READY. Nothing in the store or the page component checks this. The "Approve Ready" button appears whenever `entry.status === CatalogueStatus.INCOMPLETE` regardless of asset state. This is a business-logic gap that should be enforced either in the store action (query assets first, reject if incomplete) or via a database trigger.

## Rule-set state machine is unguarded

`transitionRuleSetStatus` takes an arbitrary string:

```ts
transitionRuleSetStatus: async (id: string, newStatus: string) => {
  await fromTable('rule_set').update({ status: newStatus }).eq('rule_set_id', id);
}
```

The UI uses `getNextStatus()` to limit the offered button to the forward transition, but the action itself doesn't validate. Any component (or future code) calling `transitionRuleSetStatus(id, 'DRAFT')` on an ACTIVE rule set would succeed silently. If the database schema has a CHECK constraint this will fail at the DB level with an obscure error; if it doesn't, data integrity is at risk.

## Delete without confirmation or cascade awareness

`deleteFamily`, `deleteCategory`, `deleteDesignFamily`, and `deleteDesignSubfamily` all fire `fromTable(...).delete().eq(...)` directly from a button click handler with no intermediate confirmation. FamilyCategoryPage:

```tsx
<button onClick={(e) => { e.stopPropagation(); deleteFamily(family.family_id); }}>
  Delete
</button>
```

If the family has child categories or SKUs referencing it via `family_id`, Supabase/Postgres will return a FK-violation error. That error surfaces as the generic red `admin-error` banner with the raw Postgres message (e.g., `"update or delete on table \"family_master\" violates foreign key constraint"`). Adding a confirmation step and a pre-check for children would improve UX significantly.

## Upload path and empty content_hash

`uploadCatalogueAsset` constructs the storage path as `${skuId}/${assetType}/${Date.now()}.${ext}`. Two uploads within the same millisecond (unlikely but possible in automated tests or rapid double-clicks) would collide silently, with the second overwriting the first. More importantly, `content_hash` is set to `''`. If any downstream process (catalogue validation, CDN cache-busting, integrity verification) relies on this field, it will get an empty string and fail or produce incorrect results.

## Test coverage gaps

The 24 new tests cover rendering presence (each page renders its `data-testid` root and key elements) and basic store action mechanics (fetch sets state, error propagates). Not tested:

- SKU form validation logic (`validateForm` function — product-type-dependent dimension rules, gh/gv range enforcement)
- Catalogue upload flow
- Rule-set JSON validation (invalid JSON in constants textarea)
- AdminRoute redirect behavior after role changes mid-session
- Concurrent action race conditions
- Delete error handling when FK violations occur

The store tests verify that `fromTable` is called and state is set, but don't exercise error-path UI behavior (e.g., error banner rendering after a failed delete).
