# Full ADMIN panel — v2 review after addressing all seven v1 concerns

This second pass covers the same ~3200 line admin panel (Zustand store, six CRUD pages, route guard, layout) after all seven issues from v1 have been addressed: per-domain loading flags replaced the shared boolean, catalogue approval checks for required asset types, rule-set transitions enforce DRAFT→ACTIVE→SUPERSEDED, deletes use `window.confirm()`, FK violations get friendly messages, upload paths include `crypto.randomUUID()`, and `content_hash` is populated with file metadata. Watch for: approval asset-presence check does not filter on `is_current`, so superseded assets could satisfy it (likely); the single `error` string is still shared across domains and can be overwritten by a concurrent action (confirmed); the catalogue approval button fires without disablement during the request, so rapid double-clicks race the server (possible).

**Verdict**: APPROVED

## High-level view

The `error` field remains a single string shared across all domains — if two concurrent actions fail, only the last-to-resolve error survives in the UI. The per-domain loading flags correctly eliminated the loading-state race, but the error field didn't get the same treatment.

The catalogue approval pre-check queries `catalogue_asset` filtered by `catalogue_entry_id` and `asset_type IN ('GEOMETRY','PATTERN','RENDER')` but does not filter on `is_current = true` or `status = 'VALID'`. Once asset versioning exists (a "supersede" flow setting old rows to `is_current: false`), stale rows would satisfy the approval check. The gap is latent today since uploads always set `is_current: true` and there is no supersede mechanism in the admin panel.

The rule-set transition guard validates against a static map using the in-memory `ruleSets` array. If the store state is stale (another admin changed the status between the last fetch and the button click), the client-side guard passes an outdated check. Server-side enforcement (a DB trigger or RLS policy) would close this gap.

## Approval asset-presence check misses `is_current` filter

In `adminStore.ts`, the approval logic:

```ts
const { data: assets, error: assetError } = await fromTable('catalogue_asset')
  .select('*')
  .eq('catalogue_entry_id', entryId)
  .in('asset_type', REQUIRED_ASSET_TYPES);
```

The `skuStore.ts` render-asset query filters on `.eq('is_current', true)` (line 168), establishing the codebase pattern that `is_current` matters for determining the "live" asset. The approval check should follow the same pattern to ensure only current, valid assets count toward readiness.

## Shared error field can be overwritten by concurrent failures

Every action's catch block writes to the same field:

```ts
set((s) => {
  const next = { ...s, isLoadingFamilies: false, error: (err as Error).message };
  return { ...next, isLoading: computeIsLoading(next) };
});
```

If `fetchFamilies` and `fetchSkus` both fail (e.g., network outage), only the last-to-resolve error message is visible. The first error is silently lost. Non-blocking in practice because errors are usually network-level (affecting all queries uniformly) or specific to one user-triggered action, but it's an asymmetry with the per-domain loading flags.

## Double-click race on approval and transitions

In `CataloguePage.tsx`, the "Approve Ready" button:

```tsx
<button
  data-testid={`approve-entry-${entry.catalogue_entry_id}`}
  onClick={(e) => { e.stopPropagation(); approveCatalogueEntry(entry.catalogue_entry_id); }}
>
  Approve Ready
</button>
```

The button is never disabled during the async operation. If a user double-clicks, two `approveCatalogueEntry` calls run concurrently — both pass the asset check (the first hasn't updated status yet), and both issue `.update({ status: 'READY' })`. The second is a no-op at the DB level (already READY), so it's not destructive, but it generates unnecessary network traffic and could briefly flash an error banner if timing is unlucky.

The same pattern exists on the rule-set transition button. A simple fix: disable buttons while their domain's loading flag is true.
