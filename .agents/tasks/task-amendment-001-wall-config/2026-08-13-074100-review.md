# Wall configuration engine with deterministic panel frame generation (v3)

All 3 issues from the v2 review are resolved: `initWallConfigStoreSync` is now called at module level, row heights use `applyRoundingWithSumCorrection`, and both `setWallConfigAndFrames` and `populateZonesFromFrames` include finalization guards. The engine, store, BOM pipeline, migration, and permission system are well-structured and pass all 1094 tests with clean types (one pre-existing unused-var only).

Watch for: `createTemplate` inserts a bare `WallGeometryType` string (`'STRAIGHT'`) into the JSONB `wall_geometry` column instead of the `WallGeometry` object that every consumer expects — `template.wall_geometry.base_width_mm` would return `undefined` for any template created through this path (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The `createTemplate` action in `templateManagementStore` was refactored to drop the `base_width_mm`/`base_height_mm` parameters (which were previously top-level template columns) but doesn't construct the `WallGeometry` JSONB object that replaced them. The `CreateTemplateDialog` collects dimensions via inputs but never passes them to the store action. Every downstream consumer — `CanvasContainer`, `publishStore`, `snapshotBuilder`, `ZonePropertiesPanel` — accesses `template.wall_geometry.base_width_mm`, which would be `undefined` for templates created through this code path.

The core wall configuration engine, the store sync, the BOM pipeline integration, the RLS migration, and the permission model are solid.

## Template creation JSONB shape mismatch

The database column `template.wall_geometry` is `JSONB NOT NULL` (confirmed in `baseline/v1.1.5_baseline.sql`). The `Template` TypeScript interface defines it as:

```typescript
export interface WallGeometry {
  type: WallGeometryType;
  base_width_mm: number;
  base_height_mm: number;
  segment_a_width_mm?: number;
  segment_b_width_mm?: number;
}
```

Every consumer reads properties from this object:

```typescript
// CanvasContainer.tsx
currentTemplate.wall_geometry.base_width_mm
// publishStore.ts
currentTemplate?.wall_geometry.base_width_mm ?? 0
// snapshotBuilder.ts
template.wall_geometry.base_width_mm
```

But `templateManagementStore.createTemplate` inserts:

```typescript
wall_geometry: data.wall_geometry,  // data.wall_geometry is WallGeometryType = 'STRAIGHT' | 'L_CORNER'
```

This inserts the JSON string `"STRAIGHT"` into the JSONB column. When fetched back and cast to `Template`, `template.wall_geometry` is the string `"STRAIGHT"`, and `"STRAIGHT".base_width_mm` evaluates to `undefined`. The canvas viewport would use the fallback `?? 3000`, but `snapshotBuilder` would store `width_mm: undefined` in the snapshot, and `publishStore` would validate against a 0×0 wall boundary.

The `CreateTemplateDialog` does collect `baseWidthMm` and `baseHeightMm` from inputs but never passes them to `createTemplate`. The fix is to:
1. Add `base_width_mm: number` and `base_height_mm: number` to the `createTemplate` data parameter
2. Construct `wall_geometry: { type: data.wall_geometry, base_width_mm: data.base_width_mm, base_height_mm: data.base_height_mm }` in the insert call
3. Pass `baseWidthMm` and `baseHeightMm` from the dialog

The `duplicateAsNewDraft` path is correct — it copies `template.wall_geometry` which is already the full object from a fetched template.

TypeScript doesn't catch this because `fromTable(table: string)` returns an untyped Supabase query builder (the table name isn't generic-parameterized), so the insert payload is `any`.
