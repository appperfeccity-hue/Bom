# Configuration-driven panel frame generation with 8 fit algorithms

This change replaces manual zone creation/resize/drag on the Designer canvas with a deterministic wall configuration engine that generates read-only panel frames from parameters (wall dimensions, rows, columns, gap, fit algorithm, intensity). It fixes all TypeScript types in `database.ts` to match actual DB column names (`template_id` not `id`, `zone_id` not `id`, etc.), introduces a `wallConfigStore` with undo/redo, extends the BOM pipeline to consume panel frames instead of zone dimensions, adds a LOCKED/ALLOWED consultant permission model for wall parameters, and delivers a SQL migration creating 4 new tables.

Watch for: `@ts-nocheck` suppresses type safety across 33 test files — any regressions introduced by the type rename (FEAT-001) in those files won't surface until the suppressions are removed (confirmed). The two Zustand stores (`wallConfigStore` and `projectStore`) both hold panel frames with no reactive subscription connecting them, requiring manual orchestration (confirmed). The BOM pipeline's "smallest N covering" algorithm and the test comments describing it use inconsistent formulas — one test expects `floor` behavior, another expects `ceil` — and the engine itself uses a covering formula not visible in this diff, so quantity correctness depends on the engine's implementation matching both (likely). RLS policies grant `DELETE` on `generated_panel_frame` but the intent is immutability per Rule 64 (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The wall configuration engine is a pure function with input validation, 8 algorithm implementations that normalize output to preserve the total width invariant, obstruction exclusion, and Rule 69 enforcement. The main risk is that floating-point panel widths can produce sub-pixel discrepancies when persisted to INT columns in Postgres, and no rounding strategy is defined.

The store layer uses two independent Zustand stores. `wallConfigStore` owns the config, permissions, and generated frames; `projectStore` has a `setWallConfigAndFrames` method that accepts frames and populates zones. There is no subscription or middleware connecting them — nothing prevents `wallConfigStore.panelFrames` and `projectStore.panelFrames` from diverging.

The BOM pipeline gains a clear priority path: when `generatedPanelFrames` is present and non-empty, zones are ignored. Panel frames in the snapshot carry no `panel_gap_mm` value, so the BOM pipeline cannot validate that the structural gap was not conflated with SKU gaps by whatever populated the snapshot.

The migration is well-structured with CHECK constraints, RLS, and unique indexes. However, `generated_panel_frame` has a `DELETE` policy despite being described as immutable (Rule 64). The `width_mm` and `height_mm` columns are INT, but the engine produces floating-point widths — the rounding strategy at persistence time is unspecified.

The 33 `@ts-nocheck` annotations across test files suppress TypeScript entirely, meaning these tests will not catch type-level regressions introduced by the interface changes. This is a significant coverage gap for a change whose primary FEAT-001 goal was type correctness.

## Wall configuration engine: float precision and persistence

The engine computes `availableWidth = total_width_mm - (columns - 1) * panel_gap_mm` then divides by columns, producing fractional results for most inputs. All non-EQUAL algorithms normalize widths by computing `scale = availableWidth / total` after applying their distribution logic.

The Rule 69 check (`columnWidths[col] < MIN_PANEL_DIMENSION`) happens after normalization, which means a pre-normalization value that drops below 50mm could pass validation if normalization pushes it back above. For extreme intensity values combined with many columns the boundary could surprise:

```typescript
// After normalization, a pre-norm value of 48mm might become 50.1mm
const scale = availableWidth / total;
return widths.map((w) => w * scale);
```

The more concrete problem is persistence. The `generated_panel_frame` table uses `INT` for `width_mm` and `height_mm`. If `3000 / 7 = 428.571...` gets rounded to 429 for each of 7 columns, the sum is 3003 — exceeding the wall. No rounding strategy is implemented in the engine or the store.

## Dual-store architecture and the coordination gap

`wallConfigStore` calls `generatePanelFrames` on every config change and stores the result locally. `projectStore` exposes `setWallConfigAndFrames(config, frames)` which a consumer must call explicitly to sync frames into the zones array. There is no `subscribe()` call connecting the two stores, and no React component in this diff that bridges them.

This means:
- `wallConfigStore.setWallConfig({columns: 5})` regenerates frames in `wallConfigStore`
- `projectStore.zones` still holds the old 3-column frames
- The canvas renders stale zones until something calls `projectStore.setWallConfigAndFrames`

The wall configuration UI panel (referenced in the requirements but not present in this diff) presumably handles this coordination. But the architecture permits the inconsistency, and tests of `wallConfigStore` don't verify that `projectStore` also updates.

## BOM pipeline: quantity formula inconsistency

The test file `bomPipelineWallConfig.test.ts` documents two different quantity formulas in its comments:

```
// Width: smallest N where N*600 + (N-1)*2 >= 1000 -> N=2 (1202 >= 1000)
```

This is a covering formula (ceiling). But later:

```
// Ncol = floor((990 + 0) / (330 + 0)) = floor(990/330) = 3
```

This is floor division. The actual `calculateWallPanels` engine (not in this diff) must use one or the other. The tests pass, so either the engine has two code paths (zero-gap uses floor, non-zero uses covering) or one of the comments is incorrect. A wrong quantity formula directly impacts procurement costs.

## Consultant permission model: snapshot shape mismatch

`snapshotBuilder.ts` writes consultant permissions as:

```typescript
consultant_permissions: wallConfigInput?.consultantPermissions ?? null,
```

Where `ConsultantWallPermissions` is `{ wall_width: 'LOCKED', wall_height: 'ALLOWED', ... }` — a flat object keyed by parameter name.

`usePermissionEnforcement.ts` reads permissions as:

```typescript
if (!snapshotData || !Array.isArray(snapshotData.consultant_permissions)) {
  return [];
}
return snapshotData.consultant_permissions as WallConfigPermission[];
```

It expects an **array** of `{ parameter_key, permission_mode }` objects and calls `Array.isArray()` on what is actually a plain object. This guard will always return `false`, causing `wallConfigPermissions` to always be empty. In CONSULTANT mode, `isWallParamAllowed` will then always return `false` (everything locked) — fail-closed but incorrect.

## @ts-nocheck proliferation

33 test files have `@ts-nocheck` added at the top. While this gets the test suite passing after the FEAT-001 type renames, it defeats the purpose of the type correctness work. The fixtures in these tests use the new field names (`template_id`, `zone_id`) but may have subtle type mismatches (missing required fields, wrong enum values) that TypeScript would catch. Some tests already have inconsistent fixture shapes visible in the diff (e.g., `wall_geometry` passed as a string in some places, as an object in others).

## Remaining zone mutation APIs in canvasStore

The `canvasStore` still exposes `copySelection`, `pasteClipboard`, and `duplicateSelection` APIs. These are unreachable from keyboard shortcuts after this change but remain callable programmatically. If the intent is that zones are fully immutable from the frontend (Rule 64, 65), these APIs should either be removed or guarded to reject panel-frame-sourced zones.

## Migration: missing `updated_at` trigger and DELETE on immutable table

Both `template_wall_configuration` and `project_wall_configuration` have `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()` columns but no trigger to automatically update them on row modification. Without a trigger or application-level code that sets `updated_at` on every update, the column will always show the creation timestamp.

The `generated_panel_frame` table has a `DELETE` policy allowing project owners to remove frames, contradicting the "immutable once generated" comment. If the workflow is delete-then-reinsert on regeneration, this should be documented. The absence of an `UPDATE` policy correctly prevents in-place mutation.
