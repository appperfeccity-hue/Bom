# Quantity resolution engines — v2 review (post-fix verification)

Four pure-function engines (wall panel, light, furniture, hidden component) calculate material quantities from zone/measurement inputs, orchestrated by `generateActualBom` on `bomStore`. This v2 pass verifies the four issues raised in the first review. All four are addressed: `calculateAxis` guards against zero/negative inputs, `evaluateCondition` coerces to `Number` for relational operators, `generateActualBom` collects partial results with per-item error capture, and input validation now covers degenerate dimensions. 432 tests pass, TypeScript strict compiles cleanly. Watch for: `EQ`/`NEQ` still use strict `===` which won't match `"5" === 5` across type boundaries (possible), and `wasteFactor` accepts negative values which silently reduce procurement below required quantity (confirmed).

**Verdict**: APPROVED

## High-level view

The `calculateAxis` infinite-loop gap is closed with guards for `panelSize <= 0`, `gap < 0`, and `zoneSize <= 0` before the while loop. The bonus `zoneSize` guard also prevents a degenerate single-panel result that would have been meaningless.

The condition evaluator's relational operators (`GT`, `LT`, `GTE`, `LTE`) now apply `Number()` coercion to both operands, eliminating the lexicographic comparison bug. The equality operators (`EQ`, `NEQ`) remain strict-typed — `"5" === 5` returns `false` — which could silently exclude components if JSON-sourced config mixes types for equality checks.

The orchestrator `generateActualBom` wraps each engine call in a try/catch, collects `EngineError` into a `GenerationError[]` alongside successful `GeneratedBomLine[]`, and re-throws non-`EngineError` exceptions. Unexpected bugs still propagate immediately rather than being silently swallowed.

One validation gap remains: `wasteFactor` is never guarded — a negative value produces `procurementQuantity < requiredQuantity`, procuring fewer panels than needed.

## Numeric coercion fix and the EQ/NEQ gap

`evaluateCondition` now applies `Number()` coercion for relational operators:

```ts
case 'GT':
  return Number(fieldValue) > Number(targetValue);
```

Non-numeric strings (e.g., `"wood"`) coerce to `NaN`, and `NaN > anything` is `false`, so relational operators applied to non-numeric fields always exclude the component. This is fail-closed behavior — the safe default for a BOM system.

The `EQ`/`NEQ` branches still use `===`, meaning `"5" !== 5`. If the condition configuration stores a numeric threshold as the string `"5"` while the runtime field arrives as the number `5`, the condition will never match. Not blocking, but worth enforcing type consistency at the config layer or coercing for equality operators too.

## wasteFactor validation gap

```ts
const procurementQuantity = Math.ceil(requiredQuantity * (1 + wasteFactor));
```

When `wasteFactor = -1`, this yields `Math.ceil(requiredQuantity * 0) = 0`. When `wasteFactor = -0.5`, this yields `Math.ceil(requiredQuantity * 0.5)` — procuring fewer panels than required. The type is `number` with no constraint. A `if (wasteFactor < 0) throw new EngineError(...)` in `calculateWallPanels` would close it.

## Test coverage gaps

Not tested: negative `wasteFactor` (the gap identified above). Also untested: `NaN` propagation when `Number("wood")` is used in a relational condition — though the behavior is correct (fail-closed), an explicit test would document the contract.
