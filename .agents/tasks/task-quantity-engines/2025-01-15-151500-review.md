# Quantity resolution engines for BOM generation

Four pure-function engines (wall panel, light, furniture, hidden component) calculate material quantities from zone/measurement inputs. Each engine receives a typed input, performs arithmetic according to the BOM spec, and returns a typed output — no I/O, no state. A `generateActualBom` method on `bomStore` orchestrates the pipeline by iterating over each product type's inputs and collecting results into a flat `GeneratedBomLine[]`. Watch for: infinite loop in `calculateAxis` when `panelSize ≤ 0` (confirmed), type-coercion surprise in `evaluateCondition` when comparing numeric strings to numbers (likely), and `generateActualBom` swallowing `EngineError` exceptions with no partial-result strategy (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The wall panel engine finds the minimum panel count whose span covers the zone, then computes symmetric trim per side and validates a 50 mm retained-width floor. A linear `while` search determines panel count, which loops forever if `panelSize` is zero or negative — the only blocking concern in the diff.

The hidden component engine evaluates trigger rules (always / condition / dependency) and applies quantity rules (fixed, per-zone, per-panel, derived-from-parent). The condition evaluator uses strict `===` / comparison operators on a `string | number` union, which may produce unexpected results when the same logical value arrives in different types at runtime.

The orchestrator in `bomStore.generateActualBom` iterates all inputs sequentially, letting any engine exception propagate unhandled. A single failing wall panel aborts the entire BOM with no partial-result semantics.

1. **Infinite loop in `calculateAxis` with zero/negative panel size** — Guard `panelSize <= 0` (and `gap < 0`) at the top of `calculateAxis` or in `calculateWallPanels` with an `EngineError`.
2. **Type coercion in `evaluateCondition`** — `GT`/`LT`/`GTE`/`LTE` operators applied to a `string | number` union rely on JS comparison semantics; `"100" > 50` is `true` but `"9" > 50` is also `true`. 3. **No partial-result handling in `generateActualBom`** — A single `EngineError` (e.g., from one zone's panels) aborts the entire pipeline. Consider try/catch per item or a result-with-errors return shape.
4. **No input validation for negative dimensions** — `W`, `H`, `w`, `h`, edge `length` are all typed as `number` but never validated as positive. Negative values produce nonsensical results silently.

## Symmetric trimming and the infinite-loop gap

`calculateAxis` uses a `while (N * panelSize + (N - 1) * gap < zoneSize)` loop to find the minimum panel count. If `panelSize` is zero, the left-hand side never grows (it stays `0` regardless of `N`), producing an infinite loop that locks the browser tab. Negative `panelSize` has the same effect. The type system allows this — `WallPanelInput.w` is `number` with no runtime guard.

```ts
// wallPanelEngine.ts:38-40
let N = 1;
while (N * panelSize + (N - 1) * gap < zoneSize) {
  N++;
}
```

A guard at the entry of `calculateAxis` throwing `EngineError` for `panelSize <= 0` eliminates this. The same reasoning applies to `gap < 0` — a negative gap shrinks the span expression and could also loop indefinitely for certain input combinations.

## Condition evaluation across types

`evaluateCondition` accepts `fieldValue: number | string | undefined` and `targetValue: number | string`, then applies `>`, `<`, `>=`, `<=` directly. JavaScript compares mixed types by coercing the string to a number when one operand is a number — but only with `<`/`>`, not with `===`. If both operands are strings, it compares lexicographically: `"9" > "50"` is `true` because `"9"` > `"5"` character-wise. If the configuration stores numeric thresholds as strings (common with JSON-sourced data), the `GT`/`LT` branches will produce wrong answers silently.

The fix is either: (a) coerce both operands to `Number` for `GT`/`LT`/`GTE`/`LTE`, or (b) narrow the type of condition values to `number` only for relational operators at the type level.

## Orchestrator exception propagation

`generateActualBom` loops over each product type array and calls the engine synchronously. Any `EngineError` propagates out immediately, discarding all previously computed lines. The current return type `GenerateActualBomOutput` has no way to express partial results or per-line errors — if partial generation is needed later, the interface will need to change to something like `{ lines: GeneratedBomLine[], errors: EngineError[] }`.

## Test coverage gaps

62 tests cover the four engines with thorough happy-path and boundary coverage including all 13 golden fixtures for wall panels.

Not tested: `generateActualBom` has zero tests. Input validation for degenerate values (zero/negative dimensions, empty edge arrays, `unitLength = 0` for lights producing division by zero in `Math.ceil`) is untested and unguarded.
