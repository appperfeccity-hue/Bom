# Authentication UI with role-based routing

Login, signup, and forgot-password pages wired through react-router-dom with dual route guards: `AuthLayout` redirects authenticated users away from auth pages, `ProtectedRoute` redirects unauthenticated users to `/login`. The Navigation component was extracted from App.tsx's inline header, gaining a logout button and preserving all role-conditional buttons. Signup passes a client-selected role to Supabase via `options.data`, and the existing `authStore` extracts that role from the JWT to drive UI gating.

Watch for: the signup role is sent as `user_metadata` but the auth store reads from `app_metadata` — without a server-side hook to copy the value, the role will be `null` after signup (confirmed). The auth subscription (`subscribeToAuthChanges`) only runs inside `App`, which is behind `ProtectedRoute` — on cold start, `isLoading` stays `true` forever since the subscription never fires for unauthenticated users (likely). No password strength validation exists client-side (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The routing architecture is a standard two-layout pattern: `AuthLayout` wraps `/login`, `/signup`, `/forgot-password` and bounces authenticated users to `/`; `ProtectedRoute` wraps `/` and bounces unauthenticated users to `/login`. Both check `isLoading` to prevent flash-of-wrong-page during the initial auth subscription callback. A catch-all route sends unknown paths to `/login`.

Signup passes the selected role inside `options.data` (which Supabase maps to `raw_user_meta_data` / `user_metadata`), but the auth store's `extractRole` function reads from `app_metadata`. Without a Supabase auth hook or database trigger that copies the role into `app_metadata` on user creation, newly registered users will always have a `null` role. The role-based buttons in Navigation and any RLS policies keyed to the JWT claim will not function for self-registered users.

The auth subscription (`subscribeToAuthChanges`) is called in `App`'s `useEffect`, but `App` only mounts inside `ProtectedRoute` — which itself blocks on `isLoading: true`. Since nothing else sets `isLoading` to `false`, a first-time visitor to `/` hits a permanent loading spinner. The subscription must be lifted to a component that always mounts (e.g., a wrapper in `main.tsx`).

`handleLogout` calls `signOut()` which clears auth state; on failure the state doesn't clear, so the user remains logged in rather than logging out with a stale token — fail-closed. But no error feedback is shown to the user.

## Signup role metadata mismatch

The `SignupPage` calls `supabase.auth.signUp` with `options: { data: { role } }`. In Supabase, the `data` field inside `options` is written to `raw_user_meta_data` / `user_metadata`. However, `extractRole` in `authStore.ts` reads exclusively from `app_metadata`:

```typescript
// authStore.ts
const role = user.app_metadata?.role as UserRole | undefined;
```

`app_metadata` is only writable by service-role keys or Supabase auth hooks — not by client-side signUp calls. Every newly registered user gets `role: null` after their first login. The CONSULTANT and DESIGNER buttons in Navigation will never appear until an external process sets `app_metadata.role`.

The fix is either:
- Add a Supabase `on_auth_user_created` hook that copies `raw_user_meta_data.role` into `raw_app_meta_data.role`.
- Modify `extractRole` to check `user_metadata` as a fallback: `user.app_metadata?.role ?? user.user_metadata?.role`.

The second option is simpler but less secure — `user_metadata` is client-writable post-signup, so a user could elevate their own role. The trigger approach is the correct production solution.

## Auth subscription circular dependency

`subscribeToAuthChanges()` is called inside `App`'s `useEffect`, but `App` is rendered inside `ProtectedRoute`. The initial store state is `isLoading: true`. The render path on cold start:

1. User visits `/` → `ProtectedRoute` renders → sees `isLoading: true` → shows spinner
2. `App` never mounts → `subscribeToAuthChanges` never called
3. Nothing sets `isLoading: false` → spinner persists indefinitely

The test suite masks this by explicitly setting `isLoading: false` in `beforeEach`. In a real browser, without the subscription callback, the loading state never resolves.

The same problem affects `/login` via `AuthLayout`: it also checks `isLoading` and shows a spinner while true. A new user visiting `/login` directly would see the auth-layout loading spinner forever.

Fix: move `subscribeToAuthChanges()` to a component that always mounts (a wrapper above `<Routes>` in `main.tsx`), or call it at store creation time outside React.

## Direct Supabase calls in page components

`LoginPage` routes through `authStore.signIn()`, which updates the store atomically. `SignupPage` and `ForgotPasswordPage` call `supabase.auth` directly. Signup shows a "check your email" message without logging in, and password reset is fire-and-forget, so this doesn't break today. But it creates an asymmetry: if the Supabase client is wrapped or replaced later, these pages will be missed. The test mocking strategy also diverges — `SignupPage` mocks at the module level rather than through the store.

## Test coverage gaps

The 17 new tests cover: login form rendering, submission, error display, loading state; signup form rendering, role options (ADMIN excluded), submission with metadata, error display, success message; auth routing for unauth → login redirect, auth → app access, auth → login redirect, and loading states in both guards.

Not tested: the Navigation component (logout flow, role-gated buttons), ForgotPasswordPage (no dedicated test file), the auth subscription lifecycle on cold start, and behavior when `signOut` throws an error.
