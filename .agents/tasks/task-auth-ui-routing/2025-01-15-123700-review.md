# Authentication UI with role-based routing

Login, signup, and forgot-password pages wired through react-router-dom with dual route guards (`AuthLayout` for public pages, `ProtectedRoute` for the app shell). The auth subscription now lives in an `AuthSubscription` wrapper above all routes in `main.tsx`, resolving the v1 cold-start deadlock. `extractRole` falls back to `user_metadata` when `app_metadata.role` is absent, so client-side signup roles are immediately visible. Both password fields enforce `minLength={6}`. Signup and password-reset flow through new `authStore` actions rather than calling Supabase directly. Navigation has 11 dedicated tests covering logout, role gating, and mode toggle.

Watch for: nothing blocking. All five v1 issues are resolved. The `user_metadata` fallback is a known trade-off — it's client-writable, so a user could theoretically self-elevate roles until a server-side hook copies role to `app_metadata`. This was acknowledged in v1 and accepted as the interim approach.

**Verdict**: APPROVED

## High-level view

The routing topology is clean: `AuthSubscription` wraps the entire `<Routes>` tree so the `onAuthStateChange` callback fires regardless of which route is active, eliminating the circular dependency where `ProtectedRoute` blocked `App` from mounting and the subscription from firing. Both layout guards check `isLoading` before making redirect decisions, preventing flash-of-wrong-page during the initial auth resolve.

The auth store now owns all auth operations — `signIn`, `signUp`, `resetPassword`, `signOut`, `subscribeToAuthChanges` — giving a single point of control for mocking in tests and for future changes to the auth provider.

Test coverage spans form behavior (login, signup), route guard logic (6 routing tests), and the Navigation component (11 tests). The ForgotPasswordPage has no dedicated test file — its error handling and success-state branching are unexercised.

## Role extraction security trade-off

```typescript
const role = (user.app_metadata?.role ?? user.user_metadata?.role) as UserRole | undefined;
if (role && ['ADMIN', 'DESIGNER', 'CONSULTANT'].includes(role)) {
  return role;
}
return null;
```

The `user_metadata` fallback means a user could set their own role to `DESIGNER` or `CONSULTANT` via the Supabase client API. This is a client-side UI concern only — RLS policies must not trust client-set metadata for authorization decisions. The whitelist guard prevents arbitrary strings from being treated as valid roles, but it cannot prevent self-elevation within the three valid values. Acceptable as an interim measure until a server-side auth hook copies role into `app_metadata`.
