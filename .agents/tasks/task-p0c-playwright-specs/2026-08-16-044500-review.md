# 41 P0-C Playwright specs and CI workflow

This change adds seven Playwright spec files containing 41 browser/API test cases in `frontend/e2e/p0-c/` and a GitHub Actions workflow at `.github/workflows/p0c-e2e.yml` to run them against the live deployment. All 41 test IDs (FUNC-001..012, CANVAS-001..014, SVG-001..008, INT-001..007) are accounted for, no production files are modified, and credentials are environment-driven. Watch for: the majority of browser tests run without authentication because they use the base `test` from `@playwright/test` instead of the auth fixture (confirmed), which means they'll exercise the login-wall or public routes rather than the authenticated UI; several tests use fallback-heavy patterns that can pass trivially when elements don't exist (likely); and the CI workflow captures the Playwright exit code in a way that can silently swallow failure (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The 30 browser-only tests (FUNC-*, CANVAS-*, SVG browser group) import the vanilla Playwright `test` and get an unauthenticated `page`. The app requires login, so every navigation will hit a login redirect or an empty state. These tests won't exercise the intended flows unless the Playwright `storageState` is wired in or the tests switch to the auth fixture's browser context. The 11 API tests (INT-003..007, SVG-003, SVG-005) correctly use the `authTest` fixture with `designerPage`/`consultantPage` requests — those will work once global-setup succeeds.

Many browser tests use defensive `if (await element.isVisible())` guards before interacting, which means an unauthenticated session that shows nothing will silently skip all assertions and report PASS. This undermines the stated requirement to "not falsely pass" and to "not convert blocked tests into passes merely because setup succeeds."

The CI workflow stores Playwright's non-zero exit code into `GITHUB_ENV` via `echo "PLAYWRIGHT_EXIT_CODE=$?" >> "$GITHUB_ENV"` — but the `||` short-circuit means `$?` reflects the exit code of `echo` (always 0), not the Playwright process. The final "fail job" step therefore never fires. Additionally, the requirement to capture video on failure is unmet because no `video` option is configured anywhere.

## Auth gap in browser tests

The existing test infrastructure establishes authentication via `global-setup.ts`, which writes JWT sessions to `.auth/designer.json` etc. The auth fixture (`auth.fixture.ts`) exposes `designerPage`, `consultantPage`, `adminPage` — but these are `APIRequestContext` instances, not browser `Page` objects with cookies. The pattern for browser auth would be to use `storageState` on a per-project basis in `playwright.config.ts`, or to perform login within each test's `beforeEach`.

The new P0-C specs import `test` from `@playwright/test` for all browser tests. This yields a clean, unauthenticated browser page. Since the app targets `bom-beryl.vercel.app` — a Supabase-authed SPA — every `page.goto('/projects')` or `/templates/...` will land on whatever the unauthenticated route is (likely a login page or redirect).

The net effect: every assertion like `await expect(page.getByRole('heading', { name: /new project/i })).toBeVisible()` will timeout because the page shows the login form, not the project creation form. The test then fails — but not because the feature is broken. It fails because the test never logged in.

```
// Current (unauthenticated):
import { test, expect } from '@playwright/test';
test('[FUNC-001]...', async ({ page }) => { ... });

// Needed: extend auth fixture to provide browser Page with storageState,
// or add a login step in beforeEach that uses the env credentials.
```

The auth fixture would need to be extended to support browser pages with `storageState`, or each browser test needs a login step.

## False-pass pattern from defensive conditionals

Multiple tests use this shape:

```typescript
const button = page.getByRole('button', { name: /finalize/i });
if (await button.isVisible()) {
  await button.click();
  // ... assertions ...
} else {
  await expect(page.getByText(/project|details/i)).toBeVisible();
}
```

When the browser hits a login wall, `button.isVisible()` returns false, the else branch runs, and the fallback assertion (`/project|details/i`) often matches generic text on the login page. The test passes without exercising the intended behavior.

This affects: FUNC-003, FUNC-004, FUNC-005, FUNC-010, INT-001, INT-002, CANVAS-010, CANVAS-011, CANVAS-012, SVG-007.

SVG-004 ("Missing asset shows placeholder") and SVG-006 ("Pattern repeat renders correctly") are extreme cases: their only unconditional assertion is `await expect(canvas.first()).toBeVisible()`, which will pass as long as *any* canvas-like element renders. They cannot distinguish between "feature works" and "page loaded something."

If a test cannot find the expected entry point, it should fail or mark itself `test.skip('Precondition not met: ...')` rather than quietly succeeding.

## CANVAS-014 permission test uses wrong fixture

`[CANVAS-014] Permission enforcement: consultant cannot edit canvas` uses the vanilla `page` (unauthenticated). To prove that a consultant sees read-only canvas, the test needs to be authenticated *as the consultant*.

The test's fallback assertion (`canvas.first().or(readOnlyIndicator).or(accessDenied)`) will match whatever the unauthenticated page renders, making it impossible to distinguish between "consultant is properly restricted" and "no one is logged in."

## CI workflow: exit-code and video gaps

The Playwright step uses:

```yaml
run: |
  npx playwright test e2e/p0-c/ \
    --reporter=html,json \
    || echo "PLAYWRIGHT_EXIT_CODE=$?" >> "$GITHUB_ENV"
```

The `$?` inside the `||` clause captures the exit code of `echo`, not of `npx playwright test`. After `||` executes, `$?` reflects the last command in the pipeline (the `echo`), which is always 0. The fix:

```yaml
run: |
  npx playwright test e2e/p0-c/ --reporter=html,json; EC=$?
  echo "PLAYWRIGHT_EXIT_CODE=$EC" >> "$GITHUB_ENV"
  exit 0
```

The video configuration is absent. `playwright.config.ts` has `screenshot: 'only-on-failure'` and `trace: 'retain-on-failure'` but no `video` setting. The CI artifact upload references traces/screenshots/videos but videos won't be generated without explicit configuration.
