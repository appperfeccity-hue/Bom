# SKU Browser panel with Zustand store, type alignment, and zone assignment

This change adds a slide-over SKU browser that allows designers to search, filter, and assign SKUs to template zones. The TypeScript interfaces for `SkuMaster` and related tables were rewritten to match the actual `sku_master` DB schema (renaming `id` to `sku_id`, dropping placeholder fields, adding all real columns). A new `skuStore` (Zustand) handles browsing state, multi-field filtering, pagination, and three-table join logic (sku_master + catalogue_entry + catalogue_asset). The UI components — SkuBrowser, SkuFilterBar, SkuGrid, SkuDetailPanel — are wired from the ZonePropertiesPanel's "Assign SKU" button and conditionally rendered in App.tsx.

Watch for: catalogue status filtering happens client-side after fetching a full page from Supabase, which skews pagination counts (confirmed). The `searchQuery` text field triggers an exact `ilike` on `sku_code` only and uses `eq` for material/colour filters, meaning the filter bar's text inputs expect exact values rather than partial matches (confirmed). No debounce on filter-triggered fetches — every keystroke in the search input fires `fetchSkus` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The type layer is a straightforward alignment with the real DB schema. Enums and interfaces now match the `sku_master`, `catalogue_entry`, `catalogue_asset`, `family_master`, `category_master`, and `sku_compatibility` tables. The `SkuWithCatalogue` join type drives all display components.

The store performs a three-step query: fetch paginated SKUs from `sku_master`, batch-fetch their catalogue entries, then batch-fetch current RENDER assets for thumbnails. The catalogue status filter is applied as a post-fetch filter in JS, not pushed to the DB query, so a page of 20 SKU rows can shrink to fewer results or zero after the filter — the pagination `totalCount` still reflects the pre-filter count from Supabase.

The UI is a fixed-position 440px panel on the right. SkuFilterBar has a `useEffect` that calls `fetchSkus()` on every filter state change, including each keystroke in the search and material/colour inputs. The SkuGrid renders a CSS grid with thumbnail placeholders, status badges, and opacity-based dimming for non-selectable items. SkuDetailPanel gates assignment behind both selectability (ACTIVE + catalogue READY) and having a zone selected.

The test suite (38 new tests) covers store state management and component rendering/interaction. The component tests override fetch actions with no-op mocks to prevent `useEffect`-driven fetches from clobbering test data.

## Client-side catalogue filtering breaks pagination

The `fetchSkus` action in `skuStore.ts` queries `sku_master` with server-side filters for product type, family, category, material, colour, SKU status, and search query. Pagination (`range(from, to)`) and count (`{ count: 'exact' }`) operate at this level. But the `catalogueStatus` filter is applied after the response comes back, in the for-loop that builds `SkuWithCatalogue[]`:

```typescript
if (filters.catalogueStatus) {
  if (!ce || ce.status !== filters.catalogueStatus) {
    continue; // skip this SKU from the results array
  }
}
```

When `catalogueStatus` is set to `READY` and half the page's SKUs are `INCOMPLETE`, the grid shows 10 items but the pagination indicator says "Page 1 of 5" based on the unfiltered 100-row count. Advancing pages may produce empty grids if all items on a given page fail the filter.

The fix is either to push this filter into the DB query (join `catalogue_entry` in the initial `select`, e.g. `sku_master!inner(*, catalogue_entry!inner(*))` with a filter on `catalogue_entry.status`), or to adjust `totalCount` after filtering and fetch additional rows to fill the page.

## No fetch debounce on filter changes

`SkuFilterBar` contains:

```typescript
useEffect(() => {
  void fetchSkus();
}, [filters, fetchSkus]);
```

`filters` is a new object reference on every `setFilter` or `setSearchQuery` call. Typing "panel" into the search input fires five `fetchSkus()` calls — one per character. Material and colour inputs have the same problem. At moderate scale this creates unnecessary load on Supabase and produces visual flicker as intermediate results flash.

A 300ms debounce on the fetchSkus call (or moving fetch triggering to blur/enter on text inputs) would eliminate the burst.

## Material and colour filters expect exact match

The store applies `.eq('material', filters.material)` and `.eq('colour', filters.colour)`. The filter bar renders these as free-text `<input>` fields, implying partial/fuzzy matching. A user typing "Oa" won't match "Oak"; they must type the exact DB value. Either switch to `.ilike('material', \`%${filters.material}%\`)` for a more natural UX, or change the UI to dropdowns populated from distinct values.

## Search placeholder vs. implementation gap

The search input's placeholder reads "Search by SKU code or material..." but the query only applies `ilike('sku_code', ...)`. This is a minor UX honesty issue — the placeholder sets an expectation the implementation doesn't fulfill. The fix is either extending the query with `.or(\`sku_code.ilike.%${q}%,material.ilike.%${q}%\`)` or changing the placeholder to "Search by SKU code...".

## Duplicated isSelectable logic

`isSelectable` is defined identically in `SkuGrid.tsx` (exported) and `SkuDetailPanel.tsx` (file-local). If the selectability rule changes (e.g., adding a future `DEPRECATED` status), both must be updated in lock-step. The `SkuGrid` version is already exported — `SkuDetailPanel` should import it.
