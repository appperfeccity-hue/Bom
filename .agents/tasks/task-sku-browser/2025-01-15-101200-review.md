# SKU Browser panel — v2 review (fix verification)

All five v1 issues have been addressed: debounce added, material/colour switched to `ilike`, search extended to cover `sku_code` and `material`, duplicate `isSelectable` removed, pagination count adjusted. TypeScript compiles cleanly and all 105 tests pass. Three new concerns remain.

Watch for: The pagination count heuristic under catalogue status filtering still produces inaccurate page totals beyond page 0 (confirmed). The search query value is interpolated raw into the PostgREST `.or()` filter string, which can break filter syntax if the input contains meta-characters like `.` or `,` (confirmed). The 300ms debounce applies uniformly to all filter changes including discrete dropdowns, adding unnecessary latency to select interactions (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The pagination fix uses `skus.length + page * pageSize` as the adjusted total when `catalogueStatus` is set. On page 0, if 8 of 20 items pass the filter, `totalCount` becomes 8 and the UI shows "Page 1 of 1" — even if page 1 has 15 matching items. Directionally better than v1's unfiltered count but still misleading for multi-page datasets.

The search query is embedded directly into the `.or()` string template without sanitizing PostgREST operators. A user searching for "panel.oak" or "oak,birch" produces a malformed filter expression, resulting in either a 400 error or silent mis-filtering.

The debounce wraps the entire `filters` dependency, so selecting a dropdown value (product type, family, category) imposes a 300ms delay before fetch. Dropdown selections are intentional discrete actions and should fire immediately; the debounce should only gate text inputs.

<details>
<summary>Issues (3)</summary>

1. **Pagination count heuristic inaccurate beyond page 0** — `skus.length + page * pageSize` only reflects the current page's filtered count, not the total across all pages. Either push catalogue status filtering into the DB query (join with filter), or fetch one extra item per page to detect "has next page" and replace numeric totals with prev/next-only navigation.
2. **Unescaped search input in `.or()` filter string** — Characters meaningful to PostgREST (`.`, `,`, `(`, `)`) in the search value will corrupt the filter expression. Sanitize or encode the value before interpolation, or switch to the Supabase JS filter builder's object syntax if available.
3. **Debounce penalizes discrete dropdown selections** — The single `useEffect` with a 300ms timeout covers all filter changes. Split the effect: immediate fetch for dropdown/enum filters, debounced fetch for text inputs only.

## Pagination count estimation under catalogue filter

The fix:

```typescript
const adjustedCount = filters.catalogueStatus
  ? skus.length + page * pageSize
  : count ?? 0;
```

This formula means the total is always "items that passed the filter on this page, plus however many items precede this page." On page 0 with 8/20 matching, totalCount = 8. On page 2 with 3/20 matching, totalCount = 43. Neither reflects reality across the full dataset.

Users may stop paging early (believing they've seen all results) or see an empty grid on later pages with a non-zero page indicator. The structural fix remains pushing the filter into the DB query: restructuring to `sku_master!inner(*, catalogue_entry!inner(*))` with `.eq('catalogue_entry.status', ...)` would give correct counts and consistent page sizes.

## Raw search input in PostgREST `.or()` string

Line 113 of `skuStore.ts`:

```typescript
query = query.or(`sku_code.ilike.%${filters.searchQuery}%,material.ilike.%${filters.searchQuery}%`);
```

PostgREST parses `.or()` strings using `.` as a field/operator separator and `,` as an expression separator. A search value of `"oak.dark"` produces `sku_code.ilike.%oak.dark%` — PostgREST interprets `dark%` as a further operator token. A value containing `,` splits into a separate filter clause entirely.

Searching for values with dots or commas either returns a Supabase 400 error or silently produces wrong results. The minimal fix is to escape these characters in the interpolated value, or to restructure using two separate `.ilike()` calls combined via the filter builder.

## Debounce granularity

```typescript
useEffect(() => {
  if (debounceRef.current) clearTimeout(debounceRef.current);
  debounceRef.current = setTimeout(() => { void fetchSkus(); }, 300);
  return () => { if (debounceRef.current) clearTimeout(debounceRef.current); };
}, [filters, fetchSkus]);
```

This triggers on any mutation of `filters`, including dropdown selects. When a user picks "WALL_PANEL" from the product type dropdown, there's a 300ms pause before results appear.

A clean split: separate the text-input-derived fields (`searchQuery`, `material`, `colour`) into their own debounced effect, and have dropdown changes call `fetchSkus()` directly via a second non-debounced effect keyed on the discrete filter fields only.
