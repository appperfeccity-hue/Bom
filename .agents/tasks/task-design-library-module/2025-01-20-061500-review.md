# Design Library with SKU availability gating

The Design Library module adds a Zustand store that fetches ACTIVE templates from Supabase, walks the template → zone → SKU → catalogue chain to compute per-template availability, then exposes client-side filtering by search text, design family, wall geometry, and availability status. The UI layer adds grouped display by design family, availability badges, blocked-reason callouts, disabled selection for BLOCKED templates, and a slide-in preview panel. Tests cover the store logic (availability computation, filters, reset) and both new UI components.

Watch for: N+1-style query fan-out with unbounded `.in()` arrays on large catalogues (confirmed); no concurrent-fetch guard allows double-firing on rapid remounts (confirmed); preview panel uses `position: fixed` with a high z-index but no backdrop/focus-trap, allowing interaction with the gallery underneath (confirmed).

**Verdict**: APPROVED

## High-level view

The availability calculation joins four tables client-side via sequential Supabase queries using `.in()` with the full set of IDs collected from each previous step. This passes unbounded arrays into PostgREST's `in` filter, which translates to a SQL `IN (...)` clause — fine for dozens of SKUs, but will hit URL length limits at hundreds.

Filtering is pure client-side post-processing: all templates are fetched once into a canonical `templates` array, then narrowed by a `filterTemplates` function on every filter state change.

The UI refactors `DesignLibrary` from a flat grid reading `projectCreationStore` to a grouped display reading the new `designLibraryStore`. The `TemplatePreviewPanel` is rendered conditionally when `selectedTemplateDetail` is non-null, but has no overlay or focus-trap, so keyboard and click events still reach the gallery behind it.

The test suite exercises availability logic, all filter paths, and component rendering in isolation. It does not test component integration or the concurrent-fetch edge case.

<details>
<summary>Issues (4)</summary>

1. **Unbounded `.in()` arrays** — `template_zone_sku`, `sku_master`, and `catalogue_entry` queries pass the full set of zone/SKU IDs without pagination or batching. For catalogues with hundreds of SKUs, this generates oversized PostgREST URLs. Batch the IDs into chunks of ~100 or move the availability check to a database function / view.
2. **No concurrent-fetch guard** — `fetchTemplatesWithAvailability` sets `isLoading` but doesn't prevent a second call from starting while the first is in flight. React StrictMode double-mounts in dev, and rapid navigation can trigger duplicate fetches that race to set state. Add an abort signal or a request-ID check.
3. **Preview panel has no backdrop** — `TemplatePreviewPanel` renders as `position: fixed` at z-index 1002 but nothing prevents interaction with the gallery behind it. A click on a card while the panel is open could trigger `selectTemplate` unintentionally. Add a backdrop div or `pointer-events: none` on the gallery when the panel is open.
4. **Templates with no zones are marked AVAILABLE by default** — The store treats "no zones" as "no blocked SKUs", which is logically correct per the current rule. But if a template has no zones because zone data hasn't been created yet (data entry in progress), it will appear available. Consider whether this matches business intent or whether zoneless templates should be filtered out or flagged.

## Availability computation and the query waterfall

```
template (ACTIVE) ──┐
                    ├──> template_zone ──> template_zone_sku ──> sku_master
design_family_master┘                                        └──> catalogue_entry
```

PostgREST encodes `.in()` values as a comma-separated list in the query string. URL length limits (typically 8KB in nginx/PostgREST default configs) will be hit around 200-300 UUIDs. For the current dataset this is unlikely to be a problem, but as the catalogue grows this will silently fail with a 414 URI Too Long. A `Promise.all` over chunked batches of 50-100 IDs, or migrating this to a Supabase RPC / database view that performs the join server-side, would eliminate the concern.

If two React effect cycles fire `fetchTemplatesWithAvailability` concurrently (StrictMode, fast navigation), both will run to completion and the second `set()` wins. This isn't a data-corruption risk but wastes network calls and can produce UI flicker. A simple guard (`if (get().isLoading) return;`) or an AbortController pattern would prevent it.

## Preview panel interaction gap

`TemplatePreviewPanel` occupies the right 600px of the viewport at `z-index: 1002`. The gallery grid remains fully interactive behind it. There's no overlay `<div>` with `onClick={clearPreview}`, no focus-trap, and no `aria-modal`. A user can scroll the gallery and click "Select" on a card while the panel is open. On narrower screens (< 900px), the panel covers most of the gallery but the uncovered portion is still clickable. Keyboard focus can tab into the gallery behind the panel.

Whether this needs fixing depends on product intent — a non-modal side panel is a valid pattern — but it should be a deliberate choice rather than an omission.

## Empty-state condition brittleness

The "No templates available" message renders only when `filteredTemplates` is empty AND all filters are at defaults:

```tsx
if (filteredTemplates.length === 0 && !filters.search && !filters.designFamilyId && !filters.wallGeometry && filters.availability === 'ALL')
```

Adding a new filter in the future requires updating this compound check. Comparing against a `defaultFilters` constant or using a helper function would be more maintainable.

## Test coverage gaps

Not tested: the behavior when `catalogue_entry` returns multiple rows for the same `sku_id` (last-write-wins in the Map, so only one status is retained per SKU — if an SKU has multiple catalogue entries with different statuses, only the last one returned by the query is checked). Not tested: component-level integration between `DesignLibrary` and `EnhancedTemplateCard` with filter-driven re-rendering. Not tested: preview panel opening from a card click and then selecting from the panel — this crosses the store boundary that's mocked in each component test.
